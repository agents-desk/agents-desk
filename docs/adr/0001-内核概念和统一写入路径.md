# 0001 内核概念和统一写入路径

- 状态：已采纳
- 日期：2026-11-19

## 背景

agents-desk 要承载客户服务、团队沟通、内部服务，以后还有审批、考勤等应用。消息来自多个渠道（网页插件、Telegram、WhatsApp、邮件……），操作的发起者既有成员，也有 AI 智能体、自动化和外部系统。

如果每个功能各写一套数据结构和写入流程，会出现这些问题：

- 同一条规则（权限、接待模式、一键停用）要在很多地方重复判断，AI 和人遵守的规则不一致；
- 实时推送、翻译、AI 响应、连接器发出、统计各自从业务代码中调用，漏掉一处就丢消息；
- 无法回答“谁在什么时候做了什么、为什么被允许”。

这些地方一旦写散，以后很难收拢，所以在第一个 PR 中把它们定下来，具体功能按需实现。

## 决定

### 内核概念

| 概念 | 是什么 |
|---|---|
| 工作区（租户） | 一个团队的空间，包含它的成员、数据和配置。代码中叫 tenant，见 [0002](0002-账号、租户与权限的域.md) |
| 参与者 | 能做事的一方：成员、团队、联系人（客户、合作方）、AI 智能体、系统 |
| 房间 | 一切会话的容器：客户会话、单聊、群聊、桥接会话。成员分内部方和外部方 |
| 事件 | 房间时间线上只追加的记录：消息、状态变化、卡片。带可见范围（所有人 / 仅内部）和派生内容（译文、语音转写） |
| 动作 | 一个有明确输入输出的操作，例如发消息、分配工单、查询订单 |
| 判定 | 决定一个动作是否执行的唯一入口 |
| 工作项 | 一件有负责人、阶段和期限的事：工单、商机、跟进任务、建议操作 |
| 连接器 | 外部聊天网络的适配器 |
| 业务集成 | 外部业务系统的接入，把它们的能力变成动作 |

新功能先找到它属于哪个概念，再决定数据和流程，不另起一套。

### 统一写入路径

所有写操作都走同一条路径：

```
外部消息 ─► 连接器 ─┐
界面、API ─────────┤
AI 智能体 ─────────┼─► 动作 ─► 判定 ─► 执行（一个事务：业务表 + 事件 + 任务） ─► 提交后分发
自动化 ───────────┘                                                    ├─ 实时推送
                                                                       ├─ 翻译、转写
                                                                       ├─ AI 响应
                                                                       ├─ 连接器发出
                                                                       └─ 统计
```

1. **动作**是 Tenon 的业务动作（`internal/<模块>/<动作>.go` 中的 `Handle`）。HTTP、队列、命令行、MCP 工具、连接器都只是入口，把外部输入转换为动作的参数，调用同一个 `Handle`。
2. **判定**是动作执行前的唯一检查点。权限、接待模式、风险等级、额度、营销许可、一键停用都在这里判断，人和 AI 遵守同一套规则；每次判定记录是哪条规则起的作用。第 1 阶段只有角色权限一类规则。
3. **执行**在一个数据库事务中写业务表、事件，以及要在后台完成的任务（Tenon 的 `queue.Topic.Publish` 传入事务）。事务回滚时，任务也不存在。
4. **分发**在事务提交之后进行：任务经队列送达实时推送、翻译、AI、连接器和统计，失败的任务按退避重试。业务代码不直接调用这些下游。
5. 每个动作写入操作日志（Tenon 的 `activity`），与业务修改在同一个事务中提交：谁、代表谁、什么时间、做了什么。

## 考虑过的做法

- **各功能自行写入，下游由业务代码直接调用**：开始时最快，但规则和下游调用会散落在各处，AI 接入后无法保证它和人遵守同样的规则。
- **事件溯源（只存事件，业务表由事件推导）**：审计和回放能力最强，但查询、迁移和调试的成本高，团队规模和阶段都用不上。我们只对房间的时间线采用只追加的事件，业务表照常读写。
- **进程内的事件总线分发下游**：实现简单，但进程崩溃时提交后的分发会丢失。改为在同一个事务中写入队列任务，由 worker 转发，保证至少一次送达。

## 后果

- 新增一个写操作，必须是一个业务动作；需要后台处理的事情在事务中发布任务，不在请求里直接调用。
- 下游处理函数要能安全地重复执行（至少一次送达）。
- 判定入口在第 3 个 PR 中落地；在那之前，权限由路由上的 `rest.RequireToken` 和动作中的检查完成，判定落地后迁移到判定入口。
- 每个动作都有操作日志，PR 1 中平台管理员的操作已经按这个方式记录。
