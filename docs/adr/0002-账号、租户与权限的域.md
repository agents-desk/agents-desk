# 0002 账号、租户与权限的域

- 状态：已采纳
- 日期：2026-11-19

## 背景

agents-desk 有三类用户：负责整套部署的平台管理员、工作区中的成员（坐席、组长、管理员、所有者），以及工作区的客户。一套部署可以有多个工作区，同一个人可能属于多个工作区，也可能同时是平台管理员。

产品中把一个团队的空间叫“工作区”，Tenon 框架中对应的概念是“租户”（tenant）：请求所在的租户、authz 的域、操作日志和设置中的 tenant 字段。如果代码中混用两个名字，每一层都要做一次转换。

以后可能为工作区提供自定义域名，所以工作区的地址不能直接当作它的身份。

## 决定

1. **工作区在代码中统一叫 tenant。** 表名 `tenants`，业务表的列名 `tenant_id`，包名 `internal/tenant`，接口路径 `/tenants`，权限 `tenants:*`。只有给用户看的文字叫“工作区”。
2. **平台管理员和工作区成员是两套账号。** 各自一张表（`platform_admins`、`members`）、一个 `identity.SubjectType`（`platform_admin`、`member`）、一个 `login.Realm`；邮箱和密码由 Tenon 的 `login` 保存。两者的登录入口和会话 cookie 分开：管理员端用 `__Host-admin`，工作区端用默认的 `__Host-session`，浏览器可以同时保持两种登录。每个 API 只接受自己的那一套账号，另一套的 token 得到 401。
3. **成员账号是全局的。** 一个人登录一次，可以属于多个工作区。他在每个工作区中的身份就是他在这个工作区中的角色：有角色即是成员，撤销全部角色即移出。
4. **权限按域分配。** 平台是域 `""`，每个工作区的域是它的 ID。角色和分配保存在 Tenon 的 `authz` 中，全局角色模板（例如 `platform-admin`、`owner`）由迁移预置，ID 固定。两个域的权限互不相通。
5. **身份和地址分开。** 工作区的 ID 是 UUIDv7，作为 Tenon 的租户、authz 的域和业务表的 `tenant_id`，永不改变；slug 是地址（`/t/{slug}/`），创建后不能修改，有保留词。请求只在一处由地址换成 ID（工作区端的租户中间件，PR 2 实现），停用检查也在这里；业务代码只见到 ID。工作区的链接只由 `tenant.Addresses` 生成。
6. **工作区有唯一的所有者。** `tenants.owner_id` 与 authz 中这个工作区的 `owner` 角色在同一个事务中修改。更换所有者时撤销原所有者的 `owner` 角色。

## 考虑过的做法

- **代码中叫 workspace**：与产品用语一致，但每一处与框架交互的地方（`sub.Tenant`、`authz` 的域、`activity` 的 tenant）都要转换，容易混淆。
- **平台管理员和成员共用一套账号**：少一张表，但平台权限和工作区权限混在一个会话中，一个工作区的管理员误获平台权限的风险更大；部署方和团队成员通常也不是同一批人。
- **slug 本身作为 ID**：省掉一次查询，但地址和身份绑死，以后无法改地址，也无法用自定义域名代替 slug。
- **每个工作区一个数据库或 schema**：隔离最强，但队列、令牌、角色都要按库区分，运维和迁移成本高。采用单库加 `tenant_id`，需要时再用 PostgreSQL 的行级安全策略兜底。

## 后果

- 属于工作区的每张表都有 `tenant_id`，唯一约束和常用索引都以它开头；每个查询都要带上 `tenant_id = sub.Tenant`，并为每个业务动作写“其他工作区访问不到”的测试。
- 以后加自定义域名：新增一张域名表，在租户中间件中先按 Host 查找，再按路径中的 slug 查找，改 `tenant.Addresses` 生成的链接；业务代码不变。
- 同一个人同时是平台管理员和成员时，有两个账号、两套密码，这是有意的分离。
- 停用的工作区在 PR 1 中只记录状态，成员不能进入的限制由 PR 2 的租户中间件实现。
