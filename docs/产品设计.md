## 1. 产品概述

agents-desk 是一个团队的综合服务平台：以 AI 为核心，以聊天为基础。主要用户是华人团队，界面以中文为主，支持多语言。

它服务三类对象：

| 对象 | agents-desk 提供什么 |
|---|---|
| 客户 | 专业的客服：客户在网站、Telegram 等渠道咨询，团队在收件箱中接待，AI 客服和 AI 助手参与；坐席和客户各自用自己的语言沟通，系统翻译 |
| 员工 | 内部的单聊、群聊；员工在企业微信、钉钉、飞书、Slack、Telegram 的群里 @ 机器人提出请求，请求进入 agents-desk，由 IT、人事、行政等团队处理 |
| 合作商家 | 商家在 Telegram 群里用机器人查订单等；合作方通过聊天链接，或者在 Telegram 上和我们的商务人员沟通，聊天记录留在 agents-desk 中，AI 也能用到 |

AI 是整个平台的基础能力，三类对象的场景都用得到：AI 客服直接接待，AI 助手帮成员处理，AI 通过业务系统接入执行查询等操作。客户服务、商家服务、内部服务各是一个 AI 用途，有自己的知识、工具和接待范围。AI 的上线方式是先由人接待、AI 辅助；会话和知识积累起来以后，管理员再选定范围让 AI 直接接待。

**第一个闭环是客服。** 先把客户咨询这一条线做完整，再扩展到商家、员工和内部聊天。第一版只做客服，数据模型和架构按通用的方式设计，能承载后面的场景：会话可以是客户咨询，也可以是外部群中的请求和内部聊天。

## 2. 用户和端

| 用户 | 是谁 | 使用的端 |
|---|---|---|
| 平台管理员 | 负责整套部署的人 | 管理员端：创建和停用工作区、平台设置（模型接口、邮件、文件存储） |
| 成员 | 工作区中的人，按权限使用不同的功能 | 工作区端：收件箱、聊天、联系人、报表、设置 |
| 客户 | 来咨询的人 | 网页聊天插件、Telegram 机器人、WhatsApp、邮件 |
| 合作商家 | 和我们有业务往来的公司及其人员 | Telegram 群中的机器人；聊天链接；Telegram 本身（我们的 Telegram 账号接入 agents-desk） |
| 员工 | 公司内部提请求的人，可以是成员，也可以只在企业微信等平台上 | 企业微信、钉钉、飞书、Slack、Telegram 群中的机器人，以群为单位接入 |
| 外部系统 | 我们的产品后端、业务系统、第三方程序 | API |

**一套部署可以有多个工作区。** 每个工作区是一个团队的独立空间，有自己的成员、渠道、数据和配置，不同的业务用不同的工作区。一个成员账号可以属于多个工作区。

**权限和角色：** 成员的权限由角色决定，每位成员在一个工作区中有一个角色。角色由管理员创建，包括：

- 会话的可见范围，三选一：全部会话；自己所在团队收件箱的和指派给自己的；只有指派给自己的；
- 可以做的操作，例如：把会话改派给别人、管理共享的快捷回复、查看报表、导出联系人、管理成员和角色、管理团队收件箱、管理渠道、管理工作区设置。

成员的角色由有“管理成员和角色”权限的其他成员修改。以后可以按成员逐项调整权限，可见范围也可以增加更多选项。

**主管理员：** 每个工作区一位，由平台管理员指定，拥有全部权限，由平台管理员更换。

团队收件箱包括成员和分配方式。管理团队的人通过角色获得相应的权限，例如能看到全部会话、改派会话、查看报表。

## 3. 核心概念

| 概念 | 是什么 |
|---|---|
| 工作区 | 一个团队的空间。所有业务数据都属于某个工作区 |
| 成员 | 工作区中的人，有权限、语言、在线状态 |
| 团队收件箱 | 一组成员共同处理服务型会话的队列，例如“一线客服”“商家支持”“IT 服务台” |
| 联系人 | 和我们沟通的一个外部的人。分两类：用户是产品传来了身份的已登录客户；线索是以访客身份发起会话的人，用浏览器中保存的编号识别，可以留下邮箱。线索登录后合并到对应的用户。一个联系人可以有多个渠道身份，可以属于一个组织 |
| 组织 | 一个外部公司，例如合作商家。联系人和外部群可以属于一个组织；AI 和业务系统按组织限定能查的数据 |
| 渠道 | 一个具体的接入点，例如某个网站上的聊天插件、某个 Telegram 机器人、某个企业微信机器人。每个渠道由一个连接器实现 |
| 外部群 | 机器人所在的一个第三方群聊，例如 Telegram 群、企业微信群。以群为单位接入：会话的对方是群，群里的人只记录名字和平台账号 |
| 会话 | 一段对话，有参与者和时间线。分两种：服务型会话和聊天型会话 |
| 服务型会话 | 需要团队处理的一件事：在收件箱中处理，有团队收件箱、负责人、状态（打开、稍后处理、已关闭）。客户咨询、外部群中的请求都是服务型会话 |
| 聊天型会话 | 长期存在的单聊或群聊：由参与聊天的人共同使用，有未读和通知。内部聊天、和合作方的商务沟通都是聊天型会话 |
| 时间线 | 会话中只追加的记录：消息、内部备注、系统事件（指派、状态变化等） |
| 参与者 | 能在会话中发言或操作的一方：联系人、外部群中的人、成员、机器人、AI、系统。AI 是一项系统功能 |
| 属性 | 联系人、组织、会话、工单上的字段。部分是内置的，管理员可以自定义 |
| 标签 | 给联系人或会话加的标记，用于筛选和统计 |
| 快捷回复 | 预先写好的回复，可以插入联系人的字段（例如名字），可以附带操作（指派、改优先级、加标签、改属性、稍后处理、关闭）。分共享的和个人的 |
| 视图 | 保存下来的筛选条件，在收件箱中作为一个列表 |
| 工单 | 需要较长时间、或者需要其他团队处理的事情 |
| 知识 | 文章、片段、网页、文档等，是 AI 回答的依据 |
| 机器人 | agents-desk 内部群聊中由程序控制的参与者，有名字和头像，可以被拉进群，用自己的 API 令牌收发消息，可以绑定一个 AI 用途（第 4 阶段） |
| AI 用途 | 一套 AI 接待的配置：用哪些知识和工具、遵守哪些指导、在哪些渠道和外部群接待。例如客户服务、商家服务、内部服务 |
| 工具 | AI 和成员可以调用的业务操作，例如查订单，由业务系统接入提供 |

概念之间的关系：

```
工作区
 ├─ 成员 ── 属于 ──► 团队收件箱
 ├─ AI 用途 ── 使用 ──► 知识、工具；在 ──► 渠道、外部群上接待
 ├─ 组织 ◄── 属于 ── 联系人、外部群
 ├─ 渠道（连接器的实例）
 │    └─ 外部群（群聊类渠道中机器人所在的群）
 ├─ 联系人 ── 有多个 ──► 渠道身份（渠道 + 外部编号）
 └─ 会话
      ├─ 种类：服务型 / 聊天型
      ├─ 对方：一个联系人，或一个外部群（服务型）；成员和联系人（聊天型）
      ├─ 参与者：联系人、外部群中的人、成员、机器人、AI
      ├─ 归属：团队收件箱、负责人或 AI（服务型）
      ├─ 状态、属性、标签
      └─ 时间线：消息、内部备注、系统事件
```

## 4. 主流程

第一版（客服）要走通的完整流程：

1. 平台管理员创建工作区，指定主管理员。
2. 管理员添加成员，建团队收件箱，设置工作时间、默认指派和翻译。
3. 管理员创建一个网页聊天插件渠道，把生成的脚本嵌入网站。
4. 客户在聊天窗口中发消息：
   - 系统找到或创建联系人；
   - 新建会话，或者把消息追加到已有的会话；
   - 会话进入默认的团队收件箱。
5. 系统按团队收件箱的分配方式指派给一位在线的坐席，或者留在队列中等坐席领取。
6. 后台识别客户消息的语言并翻译。坐席看到自己语言的译文，用自己的语言回复：
   - 发送前显示译文和回译，坐席确认；
   - 系统把译文发给客户。
7. 坐席可以：
   - 写内部备注、@ 同事；
   - 使用快捷回复；
   - 加标签、改属性；
   - 转给同事或其他团队收件箱；
   - 稍后处理。
8. 坐席关闭会话，系统请客户评价。
9. 有报表权限的成员查看会话量、响应时间和满意度。

## 5. 服务型会话

### 5.1 状态

| 状态 | 含义 |
|---|---|
| 打开 | 需要处理 |
| 稍后处理 | 暂时放下，到设定的时间或对方回复时回到打开 |
| 已关闭 | 处理完毕 |

| 从 | 到 | 触发 |
|---|---|---|
| 打开 | 稍后处理 | 成员选择稍后处理的时间 |
| 稍后处理 | 打开 | 到时间；或者对方发来消息 |
| 打开、稍后处理 | 已关闭 | 成员关闭；或者由快捷回复、AI 客服关闭 |
| 已关闭 | 打开 | 对方回复这个会话；或者成员重新打开 |

稍后处理的时间可以选：今天晚些时候、明天、下周一、一周后、一个月后，或者自定义。

### 5.2 消息归入哪个会话

| 渠道 | 规则 |
|---|---|
| 网页聊天插件 | 客户可以看到自己的会话列表，继续一个会话或发起新会话。客户回复已关闭的会话时，会话重新打开 |
| 只有一个聊天窗口的渠道（Telegram 私聊、WhatsApp） | 客户的消息追加到他最近的会话；最近的会话已关闭时，重新打开它 |
| 外部群 | 一个群一个会话：群里所有 @ 机器人的消息（以及机器人的命令）都归入这个群的会话，群里任何人发的都算；会话已关闭时，重新打开它。见 7.2 |

每条消息带渠道的外部编号，同一条消息重复送达只记录一次。

### 5.3 时间线

时间线只追加，每一项写入后保持原样。每一项有：

- 序号（会话内递增）
- 发起者（参与者）
- 类型：消息、内部备注、系统事件
- 可见范围：所有人 / 仅成员
- 内容
- 派生内容：译文、语音转写等，后台生成后补上
- 外部编号：渠道中的消息编号

消息的送达状态（发送中、已送达、已读、失败）单独记录。时间线的结构服务型和聊天型会话共用。

### 5.4 会话上的数据

- 渠道；对方：联系人或外部群
- 团队收件箱、负责人
- 状态、稍后处理的时间
- 优先级、标签、属性
- 对方的语言（取最近一条消息识别出的语言）
- 首次回复时间、关闭时间、满意度评分

### 5.5 收件箱

成员在收件箱中处理服务型会话，界面见 13.2。

- **列表：** 我的、@我、未指派、全部、各团队收件箱、视图（保存的筛选条件），都带数量。
- **会话列表：** 按状态筛选（打开、稍后处理、已关闭）；默认按等待时长排序，也可以按最近活动排序；可以批量指派、关闭。
- **会话中的操作：**
  - 回复、写内部备注（可以 @ 同事）、使用快捷回复；
  - 指派、关闭、稍后处理、打开下一个待回复的会话；
  - 设优先级、加标签、改属性。
- **查看中提示：** 显示还有谁正在看这个会话，让成员知道谁在处理。

以后增加：垃圾消息、同事的收件箱、按 SLA 到期时间排序、合并会话、导出、关注者。

## 6. 指派

服务型会话有两个归属：

- **团队收件箱**：由哪个团队处理；
- **负责人**：由哪个人处理，可以为空。

| 功能 | 说明 | 第一版 |
|---|---|---|
| 默认指派 | 新会话进入哪个团队收件箱，或直接给某位成员；自动化的指派规则优先。每个渠道、每个外部群可以设置自己的默认团队收件箱 | ✓ |
| 分配方式 | 每个团队收件箱选择：手动，或轮流分配给在线的成员 | ✓ |
| 回复即领取 | 回复一个未指派、或只指派到团队收件箱的会话时，会话归自己 | ✓ |
| 在线状态 | 在线、离开。自动分配只分给在线的成员；设为离开时可以勾选“把我的会话重新分配”，之后对方再发来消息的会话重新分配 | ✓ |
| 按负载分配 | 分给当前打开的会话最少的成员 | 以后 |
| 接待上限 | 每人同时负责的会话数，达到上限的成员暂停分配 | 以后 |
| 按规则指派 | 按渠道、语言、属性分到不同的团队收件箱 | 以后，由自动化实现 |

两个人同时领取同一个会话时，先到者生效。

**工作时间：** 工作区设置默认的工作时间和节假日，团队收件箱可以单独设置自己的工作时间。另外设置通常的回复时间（例如“几分钟内”）。聊天插件和自动化用它们告诉客户什么时候能得到回复。

## 7. 渠道

### 7.1 渠道的种类

| 渠道 | 对方 | 产生的会话 |
|---|---|---|
| 网页聊天插件 | 客户（用户、线索） | 服务型 |
| Telegram 机器人：私聊 | 客户 | 服务型 |
| WhatsApp、邮件 | 客户 | 服务型 |
| 群聊机器人：Telegram、企业微信、钉钉、飞书、Slack | 外部群 | 服务型 |
| 聊天链接 | 合作方等外部联系人 | 聊天型，见第 11 节 |
| Telegram 账号 | 合作方在 Telegram 上的单聊和群 | 聊天型，见第 11 节 |

一个渠道是一个具体的接入点，同一种渠道可以建多个。例如一个面向客户的 Telegram 机器人，一个内部和商家用的 Telegram 机器人。

### 7.2 群聊机器人和外部群

Telegram、企业微信、钉钉、飞书、Slack 的机器人用同一套规则：

- **只认群。** 会话的对方是群。群里的人只记录名字和平台账号，每条消息带上发送人，用来显示，以及回复时 @ 他。
- **一个群一个会话。** 群里所有 @ 机器人的消息和机器人命令都归入这个群的会话。第一版机器人只收 @ 它的消息和命令。
- **回复发回原来的群。** 成员或 AI 的回复由机器人发到这个群，并 @ 回复所针对的那个人。
- **群提供什么服务由群的设置决定。** 同一个机器人在商家群、内部群里提供的服务，由每个群的这几项设置决定：

  | 群的设置 | 说明 | 例子 |
  |---|---|---|
  | 所属组织 | 这个群属于哪个外部公司；留空表示内部群 | 商家群绑定到某个商家 |
  | 默认团队收件箱 | 群里的请求进入哪个团队收件箱 | 商家群进“商家支持”，内部群进“IT 服务台” |
  | AI 用途 | AI 在这个群里按哪个 AI 用途接待，决定能用哪些知识和工具；查询的数据限定在所属组织 | 商家群按“商家服务”，只能查这个商家的订单 |

- **新群先待设置。** 机器人被拉进一个新群时，这个群显示为“待设置”，AI 和工具在设置完成前保持关闭。管理员设置所属组织和 AI 用途后，群开始按设置提供服务。

### 7.3 网页聊天插件

网页聊天插件是嵌入产品网站和 App 的聊天窗口。管理员在设置中创建插件，设置名称、新会话进入的团队收件箱、问候语、主题色和允许嵌入的网站，得到嵌入代码和身份验证密钥。

**运行方式：**

| 场景 | 接入方式 | 聊天窗口 |
|---|---|---|
| 电脑浏览器 | 产品网站嵌入一段脚本，脚本在页面右下角放一个 iframe，里面是聊天窗口 | 收起时是右下角的启动按钮，展开后浮在页面上 |
| 手机浏览器 | 同上 | 收起时是右下角的启动按钮，展开后占满屏幕 |
| App（iOS、Android，以及 Flutter、React Native 等） | App 用 WebView 全屏打开聊天窗口的地址 | 占满屏幕，关闭按钮通知 App 关闭 WebView |

- 三种场景用 agents-desk 提供的同一个聊天窗口页面，它调用聊天插件的 API，经实时推送收到回复。
- **允许嵌入的网站：** 管理员列出可以嵌入这个插件的网站，聊天窗口只在这些网站中显示；列表留空表示所有网站都可以嵌入。
- **网页与聊天窗口：** 网页通过嵌入脚本的命令打开、收起聊天窗口，在用户登录、退出后传入新的身份；聊天窗口告诉网页窗口的大小和未读数。
- **App 与聊天窗口：** 通过 WebView 的脚本桥通信。App 在页面加载前传入用户身份；聊天窗口通知 App 关闭 WebView、未读数变化（App 可以在客服入口上显示角标），以及要用系统浏览器打开的链接。
- **手机上：** 软键盘弹出时输入框保持在键盘上方，界面避开刘海和底部横条，回到前台时重新连接并取回新消息。

**客户的身份：**

- **线索：** 聊天窗口第一次打开时得到一个访客编号，保存在浏览器或 App 中，之后用它识别同一位线索。
- **用户：** 产品后端用插件的身份验证密钥签名用户的身份（用户编号、名字、邮箱和有效期），网页或 App 把签名交给聊天窗口，客户作为用户进入，名字和邮箱按签名中的更新。管理员可以更换密钥，旧密钥签名的身份随即失效。
- 客户的令牌只在这个插件中有效，只能读取和发送客户自己的会话。

**聊天窗口的内容：**

- 会话列表：每个会话的状态、最后一条消息和未读数；客户可以继续一个会话，或者发起新会话。
- 聊天：客户看到所有人可见的消息，内部备注和系统事件只有成员可见；成员的消息显示成员的名字。客户读到消息后，成员看到“已读”。
- 评价：会话关闭后，客户给出 1 到 5 星，可以附一句意见。分数记为会话的满意度评分，会话重新打开后可以再次评价。
- 以后加上工单进度。

**界面语言：** 跟随客户的浏览器或手机系统的语言：中文用简体中文，其他语言用英文。

### 7.4 场景举例

| 场景 | 怎样实现 |
|---|---|
| 客户在 Telegram 上私聊机器人咨询 | Telegram 机器人渠道的私聊，进入客服团队收件箱 |
| 商家在我们的 Telegram 群里 @ 机器人查订单 | 群绑定到这个商家，按“商家服务”接待；AI 调用“查订单”工具，只能查这个商家的数据；需要人处理时，在“商家支持”收件箱中由人接手 |
| 员工在企业微信群里 @ 机器人找 IT | 企业微信机器人渠道；内部群，进入“IT 服务台”收件箱；需要较长时间处理的转成内部工单 |
| 员工在 Telegram 内部群里 @ 机器人办事 | Telegram 机器人渠道；内部群，处理方式和企业微信相同 |

## 8. 翻译

成员和对方常常用不同的语言，翻译是平台的核心功能，服务型和聊天型会话都可以使用。

- **识别：** 消息到达后，后台识别它的语言和书写方式（例如用拉丁字母写的印地语），存为消息的派生内容。太短或者属于多种语言的内容（ok、表情、订单号、链接）记为“未确定”，原样显示。自动回复、分配规则和统计直接使用识别结果。
- **客户的语言：** 取客户最近三条确定了语言的消息中最多的语言，一样多时取最近的一条：一句 ok、一段粘贴的英文报错保持原来的语言，客户连续换了语言时随之更新。成员可以在详情中手动设置客户的语言，手动设置的语言一直有效，直到改回自动识别。
- **读：** 每位成员设置自己的语言。识别的同时，消息翻译成工作区的主要语言（没有停用的成员中占比不少于 25% 或并列最多的语言，最多 3 种）。消息展示给其他语言的成员时（会话的时间线、会话列表），后台补上这位成员的语言，译好后推送到页面。每条消息的每种语言只翻译一次。成员看到译文，可以切换原文。
- **写：** 成员用自己的语言写回复。发送前，系统给出发给对方的译文，以及把译文再译回成员语言的结果；成员确认后发送。时间线中同时保存原文和发出的译文。
- **目标语言：** 取客户的语言，成员可以为这次回复另选一种语言。消息刚到、识别还在进行时，系统先完成识别再翻译回复。
- **术语表：** 产品名、品牌名按固定译法；订单号、金额、链接保持原样。
- **语气：** 亲切、中性、正式，按工作区设置默认值。
- **失败：** 翻译失败时消息照常显示，后台重试补上译文；重试也失败的，成员再次看到时补译。
- **搜索：** 原文和主要语言的译文都能搜到；其他语言的检索以后用向量等跨语言的方式提供。

翻译调用模型。模型接口（地址、密钥、模型名）在平台设置中按调用类型配置，每次调用记录用量（包括思考用的 token）和费用。识别和翻译关掉模型的思考，速度快几倍，费用低几倍。

## 9. 自动化

自动化按“触发 → 条件 → 动作”执行：

- 触发：客户打开聊天插件、发来第一条消息、会话关闭等事件；
- 条件：按联系人类型、工作时间、渠道、属性判断；
- 动作：发消息、请客户填写信息、指派、加标签、关闭会话等。

第一版只提供内置的三条，管理员可以开关：

| 时机 | 自动化 |
|---|---|
| 客户发来第一条消息时 | 告诉客户通常多久回复：工作时间内显示回复时间，非工作时间显示下次上班的时间 |
| 线索发来第一条消息时 | 请他留下联系方式 |
| 会话关闭时 | 请客户评价 |

以后开放成可视化的规则编辑，用来按规则指派、设置 SLA、把会话交给 AI 客服等。

## 10. 工单

服务型会话适合即时沟通，需要较长时间或其他团队参与的事情用工单跟进。

- **两类：**
  - 客户工单：客户能看到进度；
  - 内部工单：团队之间协作，只有成员可见。员工通过机器人提出、需要较长时间处理的请求也用内部工单。
- **工单类型：** 管理员建工单类型，例如“充值问题”。每种类型有标题、描述和自定义字段，字段用和会话相同的属性机制定义。
- **状态：** 固定 4 个：已提交、处理中、等待客户、已解决。每个状态有一个给客户看的名字，例如“等待客户”对客户显示为“等待您补充信息”；状态变化时通知客户。
- **来源：** 由会话转成，或者直接创建。转成工单时，AI 根据会话填写标题和描述。
- **客户查看：** 客户在聊天插件中查看自己的工单。

以后增加：追踪工单（一个问题影响很多客户时，关联所有相关的会话，解决后统一通知）、每个状态下自定义更细的状态、客户门户网页。状态在模型中按这 4 个大类存储，以后加的自定义状态都归入其中一个大类。

## 11. 聊天型会话

聊天型会话是长期存在的单聊和群聊，和服务型会话共用时间线、实时推送、翻译和 AI。两者的对比：

| | 服务型会话 | 聊天型会话 |
|---|---|---|
| 性质 | 一件要处理的事，办完就关闭 | 长期往来，一直保持 |
| 谁来处理 | 团队收件箱，指派给负责人 | 参与聊天的人 |
| 状态 | 打开、稍后处理、已关闭 | 未读、置顶、免打扰 |
| 参与者 | 一个对方（联系人或外部群），加上成员和 AI | 多位成员，可以加入外部联系人和机器人 |
| 衡量 | 响应时间、SLA、满意度 | 消息量、活跃度 |
| 界面 | 收件箱 | 聊天 |

**两种用法：**

- **内部聊天：** 成员之间的单聊、群聊。有未读数、已读、@ 提醒、通知、文件、搜索。
- **商务沟通：** 合作方通过聊天链接进入，和我们的商务人员聊天。
  - 聊天链接是某位成员的专属链接，合作方找的是具体的人。
  - 合作方打开链接后成为联系人，可以属于一个组织；成员可以拉入同事。
  - 以后可以增加团队的聊天链接。
  - 聊天记录留在 agents-desk 中，AI 可以用来总结、查找和回答。
- **Telegram 上的商务沟通：** 和聊天链接并列的另一种入口。合作方习惯用 Telegram，我们把一个 Telegram 账号接入 agents-desk（通过 Telegram 的客户端库 TDLib），和合作方在 Telegram 上的聊天同步到 agents-desk。
  - 只同步成员选定的单聊和群聊。
  - 双向同步：在手机 Telegram 上发的消息也出现在 agents-desk 中；接入时导入一段历史消息。
  - 账号接入后，群里的全部消息都同步。
  - 登录需要手机验证码和二步验证，由成员在界面上完成。
  - 消息都由成员确认后发出，AI 在侧栏中帮成员总结和起草。这样账号的使用方式和普通用户一致，降低被 Telegram 限制的风险。
  - 接入哪种账号（公司的商务账号或成员的个人账号）以后再定。

**AI：** 成员在聊天的侧栏中使用 AI 助手：总结聊天、查找、起草回复，结果只有自己能看到。

**机器人：** 内部群聊中可以加入机器人。机器人有名字和头像，被拉进群后：

- 外部程序可以用机器人的 API 令牌往群里发消息，例如业务系统推送订单异常、对账结果；
- 可以选择接收群里 @ 它的消息和命令，系统通过 webhook 推送给外部程序，外部程序用 API 回复；
- 可以选择绑定一个 AI 用途，群里 @ 它时由 AI 按这个用途的知识和工具回答，例如“IT 助手”。

机器人只能在它加入的群里收发消息，能做的事按它的令牌和配置检查。绑定 AI 用途让 AI 在群里有一个明确的身份。

**内部群中的内部服务：** 机器人绑定“内部服务”这类 AI 用途和一个团队收件箱时，处理方式和外部群相同：群里 @ 它的请求作为服务型会话进入团队收件箱，AI 先答，需要人处理时由人接手，回复发回原来的群。员工在企业微信的群和 agents-desk 的群中，内部服务走同一套流程。

## 12. AI

AI 是平台的基础能力，服务型会话、外部群、聊天中都能使用。

### 12.1 组成

| 部分 | 说明 |
|---|---|
| 模型接口 | 翻译、向量、对话等按调用类型分别配置地址、密钥和模型名，可以使用不同的供应商；每次调用记录用量和费用 |
| 知识 | AI 回答的依据，见 12.2 |
| 工具 | AI 可以调用的业务操作，例如查订单、查物流。业务系统通过 API 或 MCP 接入，每个工具声明参数 |
| AI 用途 | 一套 AI 接待的配置：用哪些知识和工具、遵守哪些指导、在哪里接待。见 12.4 |
| AI 客服 | 按某个 AI 用途直接接待服务型会话，见 12.5 |
| AI 助手 | 帮成员工作，结果只有成员自己能看到，见 12.3 |

**AI 在数据中的位置：** AI 是一项系统功能，权限由 AI 用途的配置决定。它在数据中出现在三处：

- 消息的发送者：时间线上标明这条消息是 AI 发的，以及按哪个 AI 用途发的；
- 会话的接待方：服务型会话可以由 AI 接待，收件箱中单独分组；
- 操作的执行者：AI 关闭会话、改属性、调用工具，时间线中的系统事件记在 AI 名下。

**AI 能做什么由 AI 用途决定。** 能调用哪些工具、能用哪些知识，都在 AI 用途中配置，权限判断按这个配置检查。查询的对象始终由系统从会话中取：客户会话中是这个联系人，外部群中是群所属的组织。

### 12.2 知识库

| 内容 | 说明 |
|---|---|
| 公开文章 | 可以发布到对外的帮助中心 |
| 内部文章 | 只给成员和 AI 助手 |
| 片段 | 简短的问答或说明，供成员和 AI 使用 |
| 网页、文档 | 同步的网站页面、上传的文件 |
| 历史会话 | 只给 AI 助手参考 |

每条内容可以分别指定给哪些 AI 用途、AI 助手、帮助中心使用。内容在后台切分并建立向量索引，用于检索。

### 12.3 AI 助手

在会话侧栏中使用，服务型会话和聊天型会话都有，结果只有当前成员能看到：

- 提问：从知识库和历史会话中找答案，并标明出处，成员可以把答案放进回复框；
- 改写：扩写、改写、调整语气、修正语法；
- 总结会话或聊天；
- 转工单时填写标题和描述。

### 12.4 AI 用途

每个 AI 用途是一套独立的配置，对应一类服务对象：

| AI 用途 | 知识 | 工具 | 接待范围 |
|---|---|---|---|
| 客户服务 | 帮助文章、产品说明，包括买家和卖家两方面的 | 查这位用户自己的订单、挂单，调度诊断 | 网页聊天插件、Telegram 私聊 |
| 商家服务 | 合作规则、结算说明 | 查这个商家的订单 | 商家的 Telegram 群 |
| 内部服务 | IT、人事、行政的制度 | 内部系统 | 企业微信、钉钉、飞书、Slack 等内部群 |

每个 AI 用途有自己的训练、测试、上线和分析：

| 部分 | 内容 |
|---|---|
| 训练 | 选择可以使用的知识和工具；用自然语言写指导（沟通风格、何时追问、何时用哪些内容、怎样处理垃圾消息）；处理流程：某一类问题的固定步骤；转人工的规则和说明；敏感话题的处理；让 AI 判断会话的属性（情绪、问题类型、紧急程度等），用于分配、转人工和报表 |
| 测试 | 扮演对方提问，看回答和依据；用历史会话中的问题批量测试 |
| 上线 | 在哪些渠道、哪些外部群、对哪些联系人（用户、线索）接待；是否先介绍自己是 AI；需要人处理时交给哪个团队收件箱；对方停止回复一段时间后跟进，再过一段时间自动关闭；是否请客户评价。可以随时暂停 |
| 分析 | 解决率、转人工率、客户评价、转给人的问题 |

一个渠道或外部群只按一个 AI 用途接待。

**AI 用途按服务对象区分。** 同一个人可能有多种身份，例如在交易平台上既是买家又是卖家；同一个渠道上也会有各种问题。这些都在一个 AI 用途内部处理：

- AI 根据问题选择用哪些知识、调哪些工具；
- 某一类问题需要固定的处理方式时，写成处理流程。例如卖家问“怎样卖得快”：查这位用户的挂单状态 → 调用调度诊断 → 按对外口径解释原因和建议；诊断结果需要人判断时转人工；
- 工具查询的数据限定在这位用户自己的，买家的订单和卖家的挂单都是他的数据；
- 交给人处理时，按 AI 判断的问题类别分到不同的团队收件箱，例如卖家调度的问题进“卖家支持”。

AI 用途的配置有版本。每次修改生成新版本，可以回滚；AI 的每次回答记录当时用的是哪个版本。

### 12.5 AI 客服

AI 客服按 AI 用途接待服务型会话。规则：

- 只依据选定的知识和工具查到的数据回答；超出这个范围的问题交给人。
- 对客户标明是 AI；客户随时可以要求转人工。
- 遇到需要成员确认的问题，可以先在会话中问成员（只有成员可见），成员回答后 AI 继续接待。
- 收件箱中为 AI 接待的会话单独分组：全部、已解决、需要成员回答、已转人工、等待中。

### 12.6 上线顺序

AI 先辅助、后接待：

1. 人工接待，AI 负责翻译；
2. 成员用 AI 助手找答案、写回复，常见问题整理进知识库；
3. 用历史会话中的问题批量测试，补齐知识和指导；
4. 在部分渠道、部分外部群或部分联系人上让 AI 客服接待，超出范围的交给人；
5. 看解决率和评价，逐步扩大范围；有问题随时暂停。

接待范围由管理员在 AI 用途的“上线”中选择。

### 12.7 第一版就要记录的数据和要留的接口

AI 的具体做法（怎样判断问题类别、怎样检索、怎样从反馈中改进）在做 AI 的阶段详细设计，并且持续迭代。下面这些第一版就要做好：数据要从第一天开始积累，接口以后改动的代价很大。

**从第一版起记录的数据：** 人工接待阶段积累的数据，就是以后训练、评测 AI 的依据。

| 数据 | 以后用来做什么 |
|---|---|
| 成员把会话转到哪个团队收件箱、改派给谁 | 训练和评估自动分流 |
| 成员给会话设的属性、标签、优先级 | 问题分类的标注数据 |
| 成员最终怎样回复，会话怎样结束（关闭、转工单、客户评价） | 构建评测集：历史问题配上当时的处理结果 |
| 每次模型调用：输入、用到的知识片段和工具结果、输出、模型、AI 用途的配置版本、用量和费用 | 回放和定位：AI 答错时，查清问题出在检索、知识还是模型理解 |

这些数据大部分已经在时间线和操作日志中，要保证完整：转派、属性的修改都作为系统事件写入时间线；模型调用单独记录，第一版的翻译调用就开始记录。

**要留的接口：** 下面几步按可替换的方式实现，以后换算法时只改这一步。

| 环节 | 接口 | 以后可以替换的实现 |
|---|---|---|
| 分类 | 收到消息后的一个步骤，结果写成会话属性（问题类别、紧急程度、情绪等） | 规则 → 大模型 → 专门的分类模型 |
| 检索 | 知识的切分、建索引、检索、重排是一条可配置的流程，索引有版本，换向量模型时重建 | 关键词和向量混合检索、重排、改写查询、跨语言检索 |
| 评测 | 评测集（问题加期望的结果），可以用任意版本的 AI 用途配置重新跑一遍 | 用大模型打分、人工标注 |

**以后迭代的方向：**

- **分类：** AI 用途由渠道和外部群直接决定；模型判断的是用途内部的问题类别，先用大模型加属性定义，数据够了再考虑专门的分类模型。
- **从错误中改进：** 发现（质检抽查、客户差评、转人工、成员标记答错）→ 定位（看用了哪些知识和工具）→ 修正（改知识、指导、工具）→ 用评测集验证 → 上线。改进的主要对象是知识和指导。
- **检索命中率：** 先区分是知识缺失（汇总成知识缺口，让人补充）、检索偏差（改检索），还是理解偏差（改指导）。知识用中文写、客户用其他语言提问时，需要跨语言检索。

### 13.2 收件箱

坐席同时接待很多会话，收件箱的设计目标是：随时看到积压情况，少找、少点。

**布局：**

```
┌──┬────────────┬──────────────┬─────────────────────────┐
│图│ 收件箱   « │ 我的         │ 会话                    │
│标│ 我的     8 │ 待回复 8 ·   │ 顶部：联系人、操作      │
│栏│ @我      3 │ 最久 42 分钟 │                         │
│  │ 未指派   5 │──────────────│ 时间线                  │
│  │ 全部    17 │ 会话列表     │                         │
│  │ 团队收件箱 │              │                         │
│  │ 视图       │              │ 回复框                  │
└──┴────────────┴──────────────┴─────────────────────────┘
```

- 四栏：图标栏、收件箱列表、会话列表、会话。详情按需打开，作为第五栏。
- **收件箱列表**约 180px：我的、@我、未指派、全部，各团队收件箱，视图，每一项带数量，随实时推送更新。可以收起，收起状态按成员记住。
- **会话列表**一直显示，约 320px。
- **详情**从会话顶部的“详情”按钮打开。窗口宽度小于约 1600px 时，打开详情会自动收起收件箱列表，关闭详情后恢复。
- **窄屏**（小于 900px）：收件箱列表和详情隐藏；会话列表和会话轮流占满，会话左上角有“返回列表”。
- 每一栏分别滚动，内容区铺满整个宽度和高度。

**会话列表：**

- 列表顶部显示当前列表的名字和积压情况：待回复数、最长的等待时间、打开的会话数。图标栏上的角标是待回复数。
- 每个会话两行：
  - 第一行：未读点、联系人名字（外部群显示群名）、渠道、等待时长；已回复的会话显示最近活动时间；
  - 第二行：最后一条消息，显示成员语言的译文。
- 等待时长：对方最后一条消息等待回复的时长。超过回复时间标黄（等待处理），超过更长的时限标深橙（需要注意），时限按工作区的回复时间设置。
- 默认按等待时长排序，等得最久的在最上面，已经回复的排在后面；也可以按最近活动排序。
- 有新消息时，列表实时调整顺序，收到消息的一行短暂高亮；当前打开的会话保持打开，成员正在输入时也保持在当前会话。
- 可以勾选多个会话，批量指派、关闭。

**会话：**

- **顶部：** 联系人名字、渠道、识别出的语言、对方的所在地和当地时间、团队收件箱；还有谁正在看这个会话；操作按钮：显示原文、指派、稍后处理、关闭、下一个待回复、详情。
- **时间线：**
  - 对方的消息在左侧，默认显示成员语言的译文，每条可以单独切换原文；顶部的“显示原文”一次切换全部；
  - 成员和 AI 的消息在右侧，显示成员写的原文，可以展开查看发给对方的译文，旁边显示送达状态（发送中、已送达、已读、失败），失败时可以重发；
  - 系统事件居中、灰色，例如“系统把会话指派给 张三”；
  - 内部备注占满一行，黄色底；
  - 按天分隔，新消息前有分隔线。
- **回复框：**
  - 回复和内部备注两种模式。内部备注时回复框变成黄色底，可以 @ 同事，内容只有成员可见。
  - 回复时，停止输入片刻后自动显示发给对方的译文和回译。发送的就是预览中的译文；预览之后原文有修改，发送前重新翻译。成员修改原文来调整译文。
  - 目标语言默认是客户的语言（见第 8 节），可以手动选择。
  - 输入 `/` 搜索快捷回复，选中后填入文字，并显示它附带的操作。
  - 发送按钮的下拉中有：发送、发送并关闭、发送并稍后处理。
  - 回车发送，Shift+回车换行；用输入法选词时按的回车只确认候选词。成员可以在偏好设置中改为 Ctrl+回车发送。
  - “发送后打开下一个待回复”：成员可以开启，回复后自动打开下一个等待最久的会话。

**详情：** 分“详情”和“AI 助手”（第 2 阶段）两个标签。详情分几部分，各部分可以折叠：

| 部分 | 内容 |
|---|---|
| 会话 | 负责人、团队收件箱、优先级、标签、会话属性，都可以直接修改 |
| 联系人 | 名字、类型、邮箱、语言、所在地和当地时间、来源页面、自定义属性、标签、备注；外部群显示群名和所属组织 |
| 最近的会话 | 同一个联系人或外部群的历史会话 |
| 以后 | 工单（第 2 阶段）、业务数据和所属组织（第 3 阶段） |

**快捷键：**

| 按键 | 操作 |
|---|---|

| `Shift+J` | 下一个待回复的会话 |
| `R` / `N` | 聚焦回复框、切换到内部备注 |
| `Ctrl+K` | 命令面板：搜索会话和联系人，执行指派、关闭、稍后处理等操作 |
| `?` | 显示全部快捷键 |

单字母快捷键在焦点位于输入框之外时生效。

**通知：** 新会话指派给我、我负责的会话有新消息、有人 @ 我时，发浏览器通知并播放提示音，成员可以在个人设置中分别开关。

## 14. 架构

### 14.1 组成

```
                  ┌──────────── 主程序（一个可执行文件）────────────┐
 网页聊天插件 ─┐  │                                                 │
 聊天链接 ─────┤  │   连接器 ──┐                                     │
 Telegram ─────┤  │            │                                     │
 企微、钉钉 ───┼─►│   API ─────┼─► 业务动作 ─► 权限判断 ─► 事务提交 │
 飞书、Slack ──┤  │            │                         │          │
 WhatsApp、邮件┘  │   AI ──────┘                         ▼          │
 工作区端 ───────►│                                  任务队列       │
 管理员端 ───────►│                                     │          │
 外部系统 ───────►│      实时推送、翻译、AI、连接器发出、自动化、统计 │
                  └─────────────────────────────────────────────────┘
                           │                 │
                        数据库            文件存储
```

- **主程序**：后端和前端打包成一个可执行文件，自行部署。
- **数据库**：保存所有业务数据。多个工作区共用一个库，每张业务表带工作区编号，每个查询都按工作区过滤。
- **任务队列**：处理提交后要做的事，失败按退避重试。
- **文件存储**：头像、附件，可以用本地目录或对象存储。
- **模型接口**：按调用类型分别配置，见 12.1。

### 14.2 写入路径

所有写操作走同一条路径：

```
入口（API、连接器、机器人、AI、自动化）
  → 业务动作
  → 权限判断
  → 一个事务：写业务表 + 追加时间线或写操作日志 + 写入要在后台执行的任务
  → 提交后：实时推送给能看到会话的成员；任务队列分发翻译、AI、连接器发出、机器人的 webhook、自动化、统计
```

- **一个用例一个业务动作。** HTTP 接口、连接器、机器人、AI、自动化、命令行都是入口，只负责把输入转成动作的参数。人和 AI 调用同一个动作，遵守同一套权限。
- **权限判断集中在一处。** 第一版只判断成员的权限；以后加入 AI 用途的配置（能用哪些工具、查哪些数据）、外部群的设置、一键停用等规则，也在这里判断，并记录是哪条规则起的作用。成员按成员的权限检查，AI 按 AI 用途的配置检查。
- **后台任务和业务数据在同一个事务中写入。** 事务回滚时任务一起回滚；提交后至少送达一次，所以处理任务的代码要能重复执行。
- **下游通过任务完成**：翻译、发消息由任务队列分发给对应的处理程序，失败时重试。实时推送在提交后直接发出，页面重新连上时自己重新读取数据。
- **每个动作都有记录**：谁、代表谁、什么时间、做了什么。会话中的动作（消息、备注、指派、关闭等）记在会话的时间线上；设置类的动作（成员、渠道、团队收件箱等）记在操作日志中。

### 14.3 连接器

每个渠道由一个连接器实现，接口统一：

| 能力 | 说明 |
|---|---|
| 收消息 | 把外部消息转换成统一的格式，带外部编号、发送人、所在的群（群聊时），交给“收到消息”的业务动作 |
| 发消息 | 把时间线中的消息发到外部渠道；群聊时指明发到哪个群、@ 谁 |
| 回执 | 送达、已读、失败 |
| 能力声明 | 支持哪些消息类型（文字、图片、文件、按钮、命令）、是否有已读回执、是否有发送时限、是否支持群聊 |
| 群事件 | 机器人被拉进群、被移出群，用来维护外部群的列表 |

连接器可以在主程序中实现，也可以作为独立进程运行，用任何语言编写。Telegram 账号的连接器基于 TDLib，作为独立进程运行，每个账号保存自己的登录状态。

### 14.4 实时推送

每个成员在每个工作区中有一个个人频道。时间线有新内容、会话的负责人或状态变化、成员标记已读时，提交后推送给修改前后能看到这个会话的成员，按可见范围、团队收件箱、负责人和被 @ 的人算出。推送只带会话的编号，页面收到后经接口重新读取，权限和语言都由接口处理。

每个会话一个频道，用来显示谁正在看这个会话、谁正在输入。聊天插件和聊天链接也通过推送收到回复和送达状态。

### 14.5 API

- 每个功能都有 API。工作区端、聊天插件、聊天链接、以后的桌面端和 App、外部系统用同一套 API。
- 浏览器用会话 cookie 携带令牌；其他程序用 API 令牌。
- 产品后端通过签名把用户身份传给聊天插件，客户由线索变成用户。

### 14.6 第一版要预留的

第一版只做客服，下面这些按通用的方式实现，后面的场景在上面扩展：

| 模型 | 第一版 | 以后 |
|---|---|---|
| 会话 | 只有服务型，对方是联系人 | 对方可以是外部群；加入聊天型会话 |
| 参与者 | 联系人、成员、系统 | 外部群中的人、机器人、AI。参与者类型按可扩展的方式设计 |
| 渠道 | 只有网页聊天插件 | 其他渠道按同一个连接器接口接入 |
| 联系人 | 用户、线索 | 可以属于组织 |
| 属性 | 联系人和会话的自定义属性 | 组织、工单类型的字段，AI 判断的属性，用同一套属性定义 |
| 自动化 | 内置的几条 | 内部按“触发 → 条件 → 动作”执行，以后开放可视化编辑 |
| 权限判断 | 成员的权限 | AI 用途的配置、外部群的设置 |
| 界面语言 | 简体中文和英文 | 文字都走翻译文件，可以增加其他语言 |
