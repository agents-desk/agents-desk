## 1. 产品概述

agents-desk 是一个在线客服系统，主要用户是华人客服团队，界面以中文为主。

客户在产品的网站或聊天软件上发起咨询，消息进入 agents-desk 的收件箱。坐席在收件箱中接待，用自己的语言阅读和回复；系统把客户的消息翻译给坐席，把坐席的回复翻译成客户的语言。

AI 分两种：

- **AI 助手**：帮坐席找答案、改写回复、总结会话，只有坐席能看到；
- **AI 客服**：直接接待客户，回答不了时交给人。

系统先由人接待、AI 助手辅助；会话和知识积累起来以后，再让 AI 客服在管理员选定的范围内接待。

以后在同一个系统中加入内部沟通（成员之间的单聊和群聊）、内部服务、与 Telegram 互通、综合工作台，并开源和商业化。内部服务指公司员工在企业微信、钉钉、飞书的群聊或单聊中 @ 机器人提出请求，请求进入 agents-desk，由 IT、人事、行政等团队处理，回复经机器人发回原来的聊天。第一版只做客服，但数据模型和架构要能承载这些扩展，见第 12 节。

## 2. 用户和端

| 用户 | 是谁 | 使用的端 |
|---|---|---|
| 平台管理员 | 负责整套部署的人 | 管理员端：创建和停用工作区、平台设置（模型接口、邮件、文件存储） |
| 成员 | 工作区中的人，按权限使用不同的功能 | 工作区端：收件箱、联系人、报表、设置 |
| 客户 | 来咨询的人 | 聊天插件（嵌入网站的聊天窗口），以后还有 Telegram、WhatsApp、邮件 |
| 员工（以后） | 公司内部提请求的人，不是 agents-desk 的成员，在 agents-desk 中作为用户类型的联系人，企业微信、钉钉、飞书的账号是他的渠道身份 | 企业微信、钉钉、飞书中的机器人 |
| 外部系统 | 我们的产品后端、第三方程序 | API |

**一套部署可以有多个工作区。** 每个工作区是一个团队的独立空间，有自己的成员、渠道、数据和配置，不同的业务用不同的工作区。一个成员账号可以属于多个工作区。

**权限：** 每位成员有一组权限，决定他能看到哪些会话、能做哪些操作。

会话的可见范围，五选一：

- 全部会话；
- 只看指派给自己的；
- 只看指派给自己所在团队收件箱的；
- 全部，但不包括指定的团队收件箱；
- 只能看到通过 @ 或链接打开的会话。

其他权限按模块分组，逐项勾选，例如：

| 模块 | 权限举例 |
|---|---|
| 收件箱 | 新建会话、把会话改派给别人、指派给自己、取消自己的指派、离开时改派自己的会话、管理会话的参与者、合并会话、删除回复、删除内部备注 |
| 快捷回复 | 管理共享的快捷回复、使用个人的快捷回复 |
| 设置 | 管理常规和安全设置；管理成员和权限；管理团队收件箱；管理聊天插件；管理工作时间 |
| 数据 | 管理工作区的数据（属性、标签）；查看联系人列表和资料；导出联系人 |
| 报表 | 查看报表；创建和编辑报表；删除报表；对外分享报表 |
| 知识库、AI 与自动化 | 管理知识、AI 客服和自动化（以后的阶段） |

**角色：** 管理员创建的一组权限，用来批量设置成员的权限。添加成员时，可以套用一个角色，也可以逐项勾选。成员不能修改自己的权限。

**主管理员：** 每个工作区一位，由平台管理员指定，拥有全部权限，其他成员不能修改或移出他。

团队收件箱只有成员和分配方式，不设负责人；需要管理团队的人，给他相应的权限即可，例如看到全部会话、改派会话、查看报表。

## 3. 核心概念

| 概念 | 是什么 |
|---|---|
| 工作区 | 一个团队的空间。所有业务数据都属于某个工作区 |
| 成员 | 工作区中的人，有权限、语言、在线状态 |
| 团队收件箱 | 一组成员共同处理的会话队列，例如“一线客服”“技术支持” |
| 联系人 | 来咨询的人。分两类：用户是产品传来了身份的已登录客户；线索是没有登录就发起会话的客户，用浏览器中保存的编号识别，可以留下邮箱。线索登录后合并到对应的用户。一个联系人可以有多个渠道身份 |
| 渠道 | 一个具体的接入点，例如某个网站上的聊天插件、某个 Telegram 机器人。每个渠道由一个连接器实现 |
| 会话 | 一次咨询。有参与者、负责人、团队收件箱、状态、属性和时间线 |
| 时间线 | 会话中只追加的记录：消息、内部备注、系统事件（指派、状态变化等） |
| 参与者 | 能在会话中发言或操作的一方：联系人、成员、AI 客服、系统 |
| 属性 | 联系人、会话（以后还有工单）上的字段。部分是内置的，管理员可以自定义 |
| 标签 | 给联系人或会话加的标记，用于筛选和统计 |
| 快捷回复 | 预先写好的回复，可以插入联系人的字段（例如名字），可以附带操作（指派、改优先级、加标签、改属性、稍后处理、关闭）。分共享的和个人的；共享的可以限定给哪些团队用、在哪些场合用（发起会话、回复、写内部备注） |
| 视图 | 保存下来的筛选条件，在收件箱中作为一个列表 |
| 工单 | 需要较长时间、或者需要其他团队处理的事情（第 2 阶段） |
| 知识 | 文章、片段、网页、文档等，是 AI 回答的依据（第 2 阶段） |

概念之间的关系：

```
工作区
 ├─ 成员 ── 属于 ──► 团队收件箱
 ├─ 渠道（连接器的实例）
 ├─ 联系人 ── 有多个 ──► 渠道身份（渠道 + 外部编号）
 └─ 会话 ── 来自一个渠道；单聊渠道中对应一个联系人，群聊渠道中对应一个群
      ├─ 参与者：联系人（群聊中可以有多个）、成员、AI 客服
      ├─ 归属：团队收件箱、负责人
      ├─ 状态、属性、标签
      └─ 时间线：消息、内部备注、系统事件
```

## 4. 主流程

第一版要走通的完整流程：

1. 平台管理员创建工作区，指定主管理员。
2. 管理员添加成员，建团队收件箱，设置工作时间、默认指派和翻译。
3. 管理员创建一个聊天插件渠道，把生成的脚本嵌入网站。
4. 客户在聊天窗口中发消息：
   - 系统找到或创建联系人；
   - 新建会话，或者把消息追加到已有的会话；
   - 会话进入默认的团队收件箱。
5. 系统按团队收件箱的分配方式指派给一位在线的坐席，或者留在队列中等坐席领取。
6. 后台识别客户消息的语言并翻译。坐席看到自己语言的译文，用自己的语言回复：
   - 发送前显示译文和回译，坐席确认；
   - 系统把译文发给客户。
7. 坐席可以：
   - 写内部备注、@ 同事；
   - 使用快捷回复；
   - 加标签、改属性；
   - 转给同事或其他团队收件箱；
   - 稍后处理。
8. 坐席关闭会话，系统请客户评价。
9. 有报表权限的成员查看会话量、响应时间和满意度。

## 5. 会话

### 5.1 状态

| 状态 | 含义 |
|---|---|
| 打开 | 需要处理 |
| 稍后处理 | 暂时放下，到设定的时间或客户回复时回到打开 |
| 已关闭 | 处理完毕 |

| 从 | 到 | 触发 |
|---|---|---|
| 打开 | 稍后处理 | 成员选择稍后处理的时间 |
| 稍后处理 | 打开 | 到时间；或者客户发来消息 |
| 打开、稍后处理 | 已关闭 | 成员关闭；或者由快捷回复、AI 客服关闭 |
| 已关闭 | 打开 | 客户回复这个会话；或者成员重新打开 |

稍后处理的时间可以选：今天晚些时候、明天、下周一、一周后、一个月后，或者自定义。

### 5.2 会话和消息的对应

- 客户在聊天插件中可以看到自己的会话列表，可以继续一个会话，也可以发起新会话。
- 客户回复已关闭的会话时，会话重新打开。聊天插件的设置中可以禁止客户回复已关闭的会话，也可以限制线索同时只有一个进行中的会话。
- 在 Telegram、WhatsApp 这类只有一个聊天窗口的渠道上，客户的消息追加到他最近的会话；最近的会话已关闭时，重新打开它。
- 在企业微信、钉钉、飞书这类群聊渠道上，机器人只收到 @ 它的消息。同一个群里所有 @ 机器人的消息都归入这个群的会话，不论是谁发的；会话已关闭时，重新打开它。每个 @ 机器人的人都是会话的参与者。成员的回复由机器人发回这个群，并 @ 回复所针对的那个人。
- 每条消息带渠道的外部编号，同一条消息重复送达只记录一次。

### 5.3 时间线

时间线只追加，不修改、不删除。每一项有：

- 序号（会话内递增）
- 发起者（参与者）
- 类型：消息、内部备注、系统事件
- 可见范围：所有人 / 仅成员
- 内容
- 派生内容：译文、语音转写等，后台生成后补上
- 外部编号：渠道中的消息编号

消息的送达状态（发送中、已送达、已读、失败）单独记录。

### 5.4 会话上的数据

- 渠道、联系人
- 团队收件箱、负责人
- 状态、稍后处理的时间
- 优先级、标签、属性
- 客户的语言（取最近一条消息识别出的语言）
- 关注者：关注这个会话、收到它的通知的成员
- 首次回复时间、关闭时间、满意度评分

### 5.5 收件箱

成员在收件箱中处理会话。

- **左侧的列表：**
  - 我的
  - @我
  - 我发起的
  - 全部
  - 未指派
  - 垃圾消息
  - 各团队收件箱
  - 同事的收件箱
  - 视图（保存的筛选条件）
- **会话列表：**
  - 按状态筛选：打开、稍后处理、已关闭；
  - 排序：最近活动、开始时间、等待时长、优先级、稍后处理的到期时间；以后加上 SLA 到期时间。
- **会话中的操作：**
  - 回复、写内部备注（可以 @ 同事）、使用快捷回复；
  - 指派、关闭、稍后处理；
  - 设优先级、加标签、改属性；
  - 合并到另一个会话、导出。
- **查看中提示：** 显示还有谁正在看这个会话，避免两人同时回复。
- **侧栏：** 负责人、团队收件箱、会话属性、联系人资料、最近的会话、联系人的备注和标签。

## 6. 指派

会话有两个归属：

- **团队收件箱**：由哪个团队处理；
- **负责人**：由哪个人处理，可以为空。

| 功能 | 说明 | 第一版 |
|---|---|---|
| 默认指派 | 新会话没有被自动化指派时，进入哪个团队收件箱，或直接给某位成员 | ✓ |
| 分配方式 | 每个团队收件箱选择：手动，或轮流分配给在线的成员 | ✓ |
| 回复即领取 | 回复一个未指派、或只指派到团队收件箱的会话时，会话归自己。工作区可以关闭这个行为 | ✓ |
| 在线状态 | 在线、离开、离开并改派。离开时可以选原因，离开的成员不再收到自动分配 | ✓ |
| 改派 | 负责人的状态是“离开并改派”时，客户再发来消息，会话重新分配；稍后处理的会话到期时，负责人已离开的，也重新分配 | ✓ |
| 按负载分配 | 分给当前打开的会话最少的成员 | 第 2 阶段 |
| 接待上限 | 每人同时负责的会话数，满了不再分配 | 第 2 阶段 |
| 按规则指派 | 按渠道、语言、属性分到不同的团队收件箱 | 第 2 阶段，由自动化实现 |

两个人同时领取同一个会话时，先到者生效。

**工作时间：** 工作区设置默认的工作时间和节假日，团队收件箱可以单独设置自己的工作时间。另外设置通常的回复时间（例如“几分钟内”）。聊天插件和自动化用它们告诉客户什么时候能得到回复。

## 7. 翻译

坐席和客户用不同的语言，翻译是这个系统的核心功能。

- **读：** 每位成员设置自己的语言。客户的消息到达后，后台识别语言和书写方式（例如用拉丁字母写的印地语）并翻译成成员的语言，存为消息的派生内容。成员看到译文，可以切换原文。
- **写：** 成员用自己的语言写回复。发送前，系统给出发给客户的译文，以及把译文再译回成员语言的结果；成员确认后发送。时间线中同时保存原文和发出的译文。
- **目标语言：** 取客户最近一条消息的语言。
- **术语表：** 产品名、品牌名按固定译法；订单号、金额、链接保持原样。
- **语气：** 亲切、中性、正式，按工作区设置默认值。
- **失败：** 翻译失败时消息照常显示，后台重试补上译文。
- **搜索：** 原文和译文都能搜到。

翻译调用模型。模型接口（地址、密钥、模型名）在平台设置中按用途配置，每次调用记录用量和费用。

## 8. 自动化

自动化按“触发 → 条件 → 动作”执行：

- 触发：客户打开聊天插件、发来第一条消息、会话关闭等事件；
- 条件：按联系人类型、工作时间、渠道、属性判断；
- 动作：发消息、请客户填写信息、指派、加标签、关闭会话等。

第一版只提供内置的几条，按用户和线索分别开关：

| 时机 | 对谁 | 自动化 |
|---|---|---|
| 打开聊天插件时 | 线索 | 要求先留下邮箱，才能开始会话 |
| 发来第一条消息时 | 用户、线索 | 告诉客户通常多久回复：工作时间内显示回复时间，非工作时间显示下次上班的时间 |
| 发来第一条消息时 | 用户 | 先请客户补充问题的情况 |
| 发来第一条消息时 | 线索 | 请客户留下联系方式 |
| 会话关闭时 | 用户、线索 | 请客户评价 |

发来第一条消息时的自动化可以设置为：工作时间内先等 2 分钟，坐席还没回复才触发。

以后开放成可视化的规则编辑，用来按规则指派、设置 SLA、把会话交给 AI 客服等。

## 9. 工单

第 2 阶段实现。会话适合即时沟通，需要较长时间或其他团队参与的事情用工单跟进。

- **三类：**
  - 客户工单：客户能看到进度；
  - 内部工单：团队之间协作，客户看不到；
  - 追踪工单：一个问题影响很多客户时，关联所有相关的会话，解决后统一通知。
- **工单类型：** 管理员在每一类下建类型，例如“充值问题”。每种类型有：
  - 自己的字段：标题、描述，加上自定义字段，字段用和会话相同的属性机制定义；
  - 用到的状态；
  - 是否由 AI 根据会话自动填写标题和描述。
- **状态：**
  - 4 个固定的大类：已提交、处理中、等待客户、已解决；
  - 每个大类下可以自定义状态；
  - 每个状态有给成员看和给客户看的两个名字，状态变化时可以通知客户。
- **来源：** 由会话转成客户工单；或者在会话中关联内部工单、追踪工单；也可以直接创建。
- **客户查看：** 客户在聊天插件中、或者在单独的客户门户网页中查看自己的工单。

## 10. 知识库和 AI

第 2、3 阶段实现。

### 10.1 知识库

| 内容 | 说明 |
|---|---|
| 公开文章 | 可以发布到对外的帮助中心 |
| 内部文章 | 只给成员和 AI 助手 |
| 片段 | 简短的问答或说明，不对外发布 |
| 网页、文档 | 同步的网站页面、上传的文件 |
| 历史会话 | 只给 AI 助手参考 |

每条内容可以分别指定给 AI 客服、AI 助手、帮助中心使用，也可以限定只对某些联系人分组使用。内容在后台切分并建立向量索引，用于检索。

### 10.2 AI 助手（第 2 阶段）

在会话侧栏中使用，结果只有当前成员能看到：

- 提问：从知识库和历史会话中找答案，并标明出处，成员可以把答案放进回复框；
- 改写：扩写、改写、调整语气、修正语法；
- 总结会话；
- 转工单时填写标题和描述。

### 10.3 AI 客服（第 3 阶段）

AI 客服是工作区中的一个参与者，可以像成员一样负责会话。

| 部分 | 内容 |
|---|---|
| 训练 | 选择可以使用的知识；用自然语言写指导（沟通风格、何时追问、何时用哪些内容、怎样处理垃圾消息）；转人工的规则和说明；敏感话题的处理；让 AI 判断会话的属性（情绪、问题类型、紧急程度等），用于分配、转人工和报表 |
| 测试 | 扮演客户提问，看回答和依据；用历史会话中的问题批量测试 |
| 上线 | 对哪些联系人（用户、线索）、在哪些渠道接待；是否先介绍自己是 AI；回答不了时交给哪个团队收件箱；客户不再回复时跟进，过一段时间自动关闭；是否请客户评价。可以随时暂停 |
| 分析 | 解决率、转人工率、客户评价、回答不了的问题 |
| 以后 | 读取联系人数据、通过数据连接器调用业务系统（例如查订单）；用自然语言写的固定处理流程 |

**规则：**

- 只依据选定的知识和查到的数据回答；回答不了时交给人。
- 对客户标明是 AI；客户随时可以要求转人工。
- 遇到需要成员确认的问题，可以先在会话中问成员（客户看不到），成员回答后 AI 继续接待。
- 收件箱中为 AI 客服的会话单独分组：全部、已解决、需要成员回答、已转人工、等待中。

## 11. 架构

### 11.1 组成

```
                  ┌──────────── 主程序（一个可执行文件）────────────┐
 聊天插件 ──┐     │                                                 │
 Telegram ─┤     │   连接器 ──┐                                     │
 WhatsApp ─┼────►│            │                                     │
 邮件 ─────┘     │   API ─────┼─► 业务动作 ─► 权限判断 ─► 事务提交 │
 工作区端 ───────►│            │                         │          │
 管理员端 ───────►│   AI 客服 ─┘                         ▼          │
 外部系统 ───────►│                                  任务队列       │
                  │                                     │          │
                  │      实时推送、翻译、AI、连接器发出、自动化、统计 │
                  └─────────────────────────────────────────────────┘
                           │                 │
                        数据库            文件存储
```

- **主程序**：后端和前端打包成一个可执行文件，自行部署。
- **数据库**：保存所有业务数据。多个工作区共用一个库，每张业务表带工作区编号，每个查询都按工作区过滤。
- **任务队列**：处理提交后要做的事，失败按退避重试。
- **文件存储**：头像、附件，可以用本地目录或对象存储。
- **模型接口**：翻译、向量、对话等按用途分别配置，可以使用不同的供应商。

### 11.2 写入路径

所有写操作走同一条路径：

```
入口（API、连接器、AI 客服、自动化）
  → 业务动作
  → 权限判断
  → 一个事务：写业务表 + 追加时间线 + 写入要在后台执行的任务 + 操作日志
  → 提交后，任务队列分发：实时推送、翻译、AI、连接器发出、自动化、统计
```

- **一个用例一个业务动作。** HTTP 接口、连接器、AI 客服、自动化、命令行都是入口，只负责把输入转成动作的参数。人和 AI 调用同一个动作，遵守同一套权限。
- **权限判断集中在一处。** 第一版只判断成员的权限；以后加入 AI 的执行范围、一键停用等规则，也在这里判断，并记录是哪条规则起的作用。
- **后台任务和业务数据在同一个事务中写入。** 事务回滚时任务也不存在；提交后至少送达一次，所以处理任务的代码要能重复执行。
- **业务代码不直接调用下游**（推送、翻译、发消息），都通过任务完成。
- **每个动作写操作日志**：谁、代表谁、什么时间、做了什么。

### 11.3 连接器

每个渠道由一个连接器实现，接口统一：

| 能力 | 说明 |
|---|---|
| 收消息 | 把外部消息转换成统一的格式，带外部编号，交给“收到消息”的业务动作 |
| 发消息 | 把时间线中的消息发到外部渠道 |
| 回执 | 送达、已读、失败 |
| 能力声明 | 支持哪些消息类型（文字、图片、文件、按钮）、有没有已读回执、有没有发送时限、是不是群聊（群聊中发消息时要指明发到哪个群、@ 谁） |

连接器可以在主程序中实现，也可以作为独立进程运行，用任何语言编写。

### 11.4 实时推送

每个会话一个频道，每个成员一个个人频道。时间线有新内容、会话的负责人或状态变化时推送；聊天插件也通过推送收到坐席的回复和送达状态。

### 11.5 API

- 每个功能都有 API。工作区端、聊天插件、以后的桌面端和 App、外部系统用同一套 API。
- 浏览器用会话 cookie 携带令牌；其他程序用 API 令牌。
- 产品后端通过签名把用户身份传给聊天插件，客户由线索变成用户。

## 12. 以后的扩展

第一版的模型按通用的方式实现，以后的功能在这些模型上扩展：

| 以后的功能 | 建立在什么上 |
|---|---|
| 更多渠道（Telegram、WhatsApp、邮件） | 新的连接器 |
| 内部沟通 | 会话的参与者只有成员时，就是内部的单聊和群聊 |
| Telegram 互通 | 以成员本人的身份连接 Telegram 的连接器，成员在 agents-desk 中和仍在用 Telegram 的人沟通 |
| AI 客服、其他 AI 智能体 | 参与者；走同一条写入路径和权限判断 |
| 内部服务 | 企业微信、钉钉、飞书机器人的连接器：员工在群聊或单聊中 @ 机器人，每个群一个会话，进入 IT、人事、行政等团队收件箱，提问的员工是用户类型的联系人；回复由机器人发回原来的聊天。需要较长时间处理的，转成内部工单 |
| 综合工作台 | 视图的筛选对象从会话扩展到工单、内部请求、待办 |
| 可视化自动化、SLA、按规则指派 | 自动化的“触发 → 条件 → 动作” |
| 英文等界面语言 | 界面文字走翻译文件 |
| 开源、云服务、商业化 | 多工作区、自行部署、模型接口可配置 |
