## 1. 定位

agents-desk 是给华人客服团队用的客服系统：后台是中文，坐席用中文工作，客户用自己的语言咨询。它先为我们团队的产品提供客服，以后扩展到内部沟通、内部服务、Telegram 融合和综合工作台，并开源、商业化。

我们参照 Intercom 设计，原因是它是目前最成熟的客服系统之一。我们不直接用 Intercom，原因是：

- 后台没有中文；
- 不符合国内团队的使用习惯；
- 功能多，上手难。

---

## 2. 设计依据

1. **以 Intercom 为蓝本。** 概念、流程、AI 的做法沿用 Intercom，只在下面三种情况改动：
   - 华人客服需要的：中文后台、坐席看译文、发出前回译确认；
   - 为了简单而删减的；
   - 为以后扩展而预留的。
2. **华人客服为主。** 界面、用词、默认值按说中文的客服团队设计，客户的语言由系统翻译。
3. **先走通 MVP。** 第一版只做客服的完整闭环：客户发起咨询 → 分给坐席 → 坐席回复 → 关闭 → 评价 → 报表。
4. **简单，但不写死。** 渠道、参与者、属性、工单类型、收件箱视图、自动化在第一版就按通用的模型实现，只是开放的选项少。以后加内部沟通、内部服务、Telegram 融合、综合工作台时，扩展这些模型，不推倒重来。
5. **AI 原生，人先接待。** 与 Intercom 一样，AI 有两个角色：
   - AI 客服（Intercom 的 Fin），直接回复客户；
   - AI 助手（Intercom 的 Copilot），帮坐席回答。
   
   上线顺序不同：先由人接待，AI 助手辅助，会话和知识积累起来以后，再让 AI 客服在限定的范围内接待，见 11.3。

## 4. 核心概念

| 概念 | 是什么 | Intercom |
|---|---|---|
| 工作区 | 一个团队的空间，有自己的成员、渠道、数据和配置。不同的业务用不同的工作区 | Workspace |
| 成员 | 工作区中的人，按角色有不同权限 | Teammate |
| 团队收件箱 | 一组成员共同处理的会话队列，例如“一线客服”“技术支持” | Team inbox |
| AI 客服 | 工作区中的 AI 参与者。可以负责会话，在收件箱中和成员并列显示 | Fin |
| 联系人 | 来咨询的人：访客（未登录）或用户（产品传来了身份） | Visitor、Lead、User |
| 会话 | 客户的一次咨询。有负责人、状态、属性和时间线 | Conversation |
| 工单 | 需要更长时间、或者需要其他团队处理的事情，由会话转成，或者直接创建 | Ticket |
| 渠道 | 客户联系我们的地方：网页聊天插件、邮件、Telegram、WhatsApp | Channel |
| 属性 | 联系人、会话、工单上的字段，可以由管理员自定义 | Attribute |
| 快捷回复 | 预先写好的回复，可以附带操作（设标签、指派、关闭） | Macro |
| 知识 | 文章、片段、网页、文档、历史会话，是 AI 回答的依据 | Knowledge |

## 5. 聊天插件

客户在产品的网站上通过聊天插件联系我们，对应 Intercom 的 Messenger。

- **安装：** 在网站中嵌入一段脚本，右下角出现聊天按钮。
- **身份：** 未登录的客户是访客，用浏览器中保存的编号识别。产品的后端可以签名传来用户身份，客户成为用户，换设备也能看到历史。
- **消息页：** 客户看到自己的会话列表，可以继续一个会话，也可以发起新会话。与 Intercom 一样，客户回复一个已关闭的会话时，这个会话重新打开。
- **回复时间：** 工作时间内显示“通常在几分钟内回复”，非工作时间显示下次上班的时间，并请客户留下邮箱。
- **评价：** 会话关闭后，请客户打分。
- **外观：** 颜色、标志、欢迎语、显示的名字。
- **以后增加：**
  - 首页，放帮助文章和公告；
  - 帮助页，即帮助中心；
  - 工单页，客户在这里查看工单的进度；
  - App 的 SDK。

## 6. 收件箱

### 6.1 布局

与 Intercom 相同，四栏：

1. **收件箱列表**
   - 我的
   - @我
   - 我创建的
   - 全部
   - 未指派
   - 各团队收件箱
   - 视图（保存的筛选条件）
2. **会话列表**
   - 筛选：打开、稍后处理、已关闭
   - 排序：最新、最早、等待最久
3. **会话**
   - 时间线：消息、内部备注、操作记录
   - 回复框
4. **侧栏**
   - 详情：负责人、团队收件箱、属性、标签、联系人资料、最近的会话
   - AI 助手（第 2 阶段）

### 6.2 会话的状态

| 状态 | 含义 |
|---|---|
| 打开 | 需要处理 |
| 稍后处理 | 暂时放下，到设定的时间、或者客户回复时，回到打开 |
| 已关闭 | 处理完毕。客户再回复时重新打开 |

“稍后处理”的选项与 Intercom 相同：今天晚些时候、明天、下周一、一周后、一个月后、自定义。

### 6.3 回复框

- **回复：** 发给客户，按客户的语言翻译，见第 9 节。
- **内部备注：** 只有成员能看到，可以 @ 同事。
- **快捷回复：** 输入 `/` 搜索，可以附带操作（设标签、改属性、指派、稍后处理、关闭）。分个人和团队两级。
- **快捷键：** 关闭、稍后处理、指派、切换会话都有快捷键。

### 6.4 会话上的操作

- 指派给成员或团队收件箱
- 关闭、稍后处理
- 设优先级、加标签、改属性
- 合并到另一个会话
- 转为工单（第 2 阶段）
- 导出

另外，查看中提示：显示还有谁正在看这个会话，避免两人同时回复。

## 7. 指派

与 Intercom 相同，会话有两个归属：

- **团队收件箱**，表示由哪个团队处理；
- **负责人**，表示由团队中的哪个人处理。

| 设置 | 内容 | MVP |
|---|---|---|
| 默认指派 | 新会话进入哪个团队收件箱或给谁 | ✓ |
| 回复即领取 | 回复一个未指派的会话时，会话归自己 | ✓ |
| 团队收件箱的分配方式 | 手动，或者轮流分配给在线的成员 | ✓ |
| 在线状态 | 在线、离开。离开时可以选原因，不再收到新的自动分配 | ✓ |
| 重新指派 | 负责人离开时，客户再回复的会话重新分配 | ✓ |
| 接待上限 | 每人同时负责的会话数，满了就不再分配 | 第 2 阶段 |
| 按规则指派 | 按渠道、语言、联系人属性分到不同的团队收件箱 | 第 2 阶段，用自动化实现 |

## 8. 工单

工单在第 2 阶段上线。设计沿用 Intercom，这里先定下模型。

- **三类工单：**
  - 客户工单：客户可以看到进度；
  - 内部工单：在团队之间协作，客户看不到；
  - 追踪工单：一个问题影响很多客户时，关联所有相关的会话，解决后一次通知所有人。
- **工单类型：** 管理员可以在每一类下面建工单类型，例如“充值问题”“账号申诉”，每种类型有自己的字段。
- **状态：**
  - 状态分 4 个固定的大类：已提交、处理中、等待客户、已解决。
  - 每个大类下面可以自定义状态。
  - 每个状态有两个名字，一个给成员看，一个给客户看。
  - 状态变化时可以通知客户。
- **创建：** 坐席把会话转为客户工单；或者在会话中关联一张内部工单或追踪工单。AI 根据会话填写标题和描述。

## 9. 翻译

这是 agents-desk 与 Intercom 差别最大的地方，因为坐席读不懂客户的语言。

| | Intercom | agents-desk |
|---|---|---|
| 坐席看到的 | 工作区默认语言的译文 | 每位成员自己设置的语言的译文，默认中文；可以切换原文 |
| 坐席发出的 | 自动译成客户的语言 | 自动译成客户的语言；发送前显示译文和译回中文的结果，坐席确认后发送 |
| 术语表 | 有 | 有：产品名、品牌名按固定译法；订单号、金额、链接保持原样 |
| 语气 | 亲切、中性、正式 | 相同 |

- 每条消息单独识别语言和书写方式，例如用拉丁字母写的 Hinglish。回复跟随客户最近一条消息的语言。
- 快捷回复、内部备注同样按读者的语言显示。
- 原文和译文都能搜索。
- 翻译失败时，消息照常显示，译文稍后补上。

## 10. 知识库

知识库在第 2 阶段上线，供 AI 助手和 AI 客服使用。帮助中心在第 3 阶段对外发布。结构沿用 Intercom 的知识中心。

| 内容 | 是什么 | 用途 |
|---|---|---|
| 公开文章 | 帮助文章 | AI 客服、AI 助手；可以发布到帮助中心 |
| 内部文章 | 内部流程、规则 | 只给 AI 助手和成员用 |
| 片段 | 简短的问答或说明，不发布 | AI 客服、AI 助手 |
| 网页 | 同步一个网站的公开页面 | AI 客服、AI 助手 |
| 文档 | 上传的 PDF 等 | AI 客服、AI 助手 |
| 历史会话 | 最近几个月的会话 | 只给 AI 助手用 |
| 快捷回复 | 已有的快捷回复 | AI 助手推荐给坐席 |

每条内容可以分别选择给谁用：AI 客服、AI 助手、帮助中心。

## 11. AI

### 11.1 AI 助手（Copilot）

第 2 阶段上线。坐席在会话侧栏中使用，结果只有自己能看到。

- **提问：** 坐席用中文问，AI 助手从知识库和历史会话中找答案，标明出处。坐席可以把答案放进回复框，修改后发送。
- **改写：** 扩写、改写、更正式、更亲切、修正拼写和语法。
- **总结：** 一键总结会话。转接或交接时自动总结。
- **自动填写：** 转工单时，填写标题和描述。

### 11.2 AI 客服（Fin）

第 3 阶段上线。页面结构沿用 Intercom 的四步。

**训练**

| 项 | 内容 |
|---|---|
| 内容 | 从知识库中选择 AI 客服可以使用的内容 |
| 指导 | 用自然语言写的要求。分 5 类：沟通风格、何时追问、何时使用哪些内容、垃圾消息、其他 |
| 转人工 | 规则（按属性判断，确定执行），加上自然语言的转人工指导 |
| 敏感话题 | 遇到敏感话题时怎样处理，对应 Intercom 的 Safety Guard |
| 数据（以后） | 读取联系人属性；通过数据连接器调用业务系统，例如查订单 |
| 流程（以后） | 用自然语言写的固定处理步骤 |

**测试**

- 预览：扮演客户提问，看回答和依据。
- 批量测试：从历史会话中生成问题，或者手动输入、导入，一次看所有回答。

**上线**

按 Intercom 的简单上线方式，一页设置：

- 对谁：访客、用户；
- 在哪些渠道；
- 是否先自我介绍是 AI；
- 回答不了时交给哪个团队收件箱；
- 客户不再回复时，多久跟进、多久关闭；
- 是否请客户评价。

可以随时暂停。

**分析**

解决率、转人工率、客户评价、回答不了的问题。

**AI 客服的规则（与 Intercom 相同）**

- 只依据选定的内容回答；找不到依据时说明并转人工。
- 对客户标明是 AI；客户随时可以要求转人工。
- 在收件箱中有自己的分组：AI 正在处理的、已解决的、需要同事回答的、已转人工的。
- **需要同事回答：** AI 遇到不会的问题，先在会话中问成员，成员回答后由 AI 继续接待。

### 11.3 从人工到 AI 的过程

我们曾经让 AI 先接待客户，AI 乱回答，造成了很多问题。这一次按下面的顺序推进。每一步用的都是 Intercom 已有的机制，没有另外发明规则。

| 步骤 | 做什么 | 积累什么 |
|---|---|---|
| 1. 人工接待 | 坐席在收件箱中回复，系统负责翻译 | 会话、快捷回复 |
| 2. AI 助手辅助 | 坐席用 AI 助手找答案、写回复；把常见问题整理成文章和片段 | 知识库 |
| 3. 测试 AI 客服 | 用历史会话中的问题批量测试，看 AI 客服能答对多少，补齐知识和指导 | 测试结果 |
| 4. 小范围上线 | AI 客服只在一部分渠道或一部分联系人上接待（例如只接待访客），回答不了的交给人 | AI 客服的会话 |
| 5. 扩大范围 | 看解决率和客户评价，逐步扩大渠道和人群；有问题随时暂停 | |

放权的范围由管理员在“上线”页中选择，系统不设自动升级或降级的阈值。

## 12. 联系人

- **类型：** 访客、用户。访客留下邮箱后仍是访客，带上邮箱。
- **资料：**
  - 名字、邮箱、语言、所在地、浏览器；
  - 第一次来的页面、来源网址和广告参数；
  - 标签、自定义属性；
  - 历史会话。
- **列表：** 按属性筛选，保存为分组。
- **合并：** 同一个人的多个身份可以合并。例如访客登录后，访客的会话归到用户名下。

## 15. MVP

### 15.1 流程

1. 平台管理员创建工作区，指定主管理员。
2. 主管理员邀请成员，建团队收件箱，设置工作时间、默认指派和翻译。
3. 管理员把聊天插件装到网站上。
4. 客户发起会话 → 进入团队收件箱 → 轮流分配或由坐席领取。
5. 坐席看译文、用中文回复，确认译文后发送。可以使用快捷回复、内部备注，也可以指派给同事。
6. 坐席关闭会话，或者稍后处理。客户评价。
7. 组长在报表中查看响应时间和满意度。

### 15.2 范围

| 包含 | 不包含 |
|---|---|

## 16. 为以后预留

第一版只开放少量选项，但下面这些模型按通用的方式实现：

| 模型 | MVP 中的样子 | 以后怎样扩展 |
|---|---|---|
| 会话 | 联系人和成员之间的对话 | 参与者可以是联系人、成员、AI 客服。只有成员参加的会话就是内部的单聊和群聊，用于内部沟通 |
| 渠道 | 只有网页聊天插件 | 每个渠道是一个连接器，收发消息的接口相同。Telegram、WhatsApp、邮件按这个接口接入；Telegram 融合是以成员本人的身份连接 Telegram 的连接器 |
| 参与者 | 成员、联系人 | AI 客服、其他 AI 智能体、系统都是参与者，可以负责会话、发消息，每次操作都有记录 |
| 工单 | 暂不开放 | 内部服务就是成员提交的内部工单，例如找 IT、人事、行政 |
| 收件箱视图 | 固定的几个收件箱和保存的筛选 | 筛选对象扩展到工单、内部请求、待办，就是综合工作台 |
| 属性 | 联系人和会话的自定义属性 | 工单类型的字段、AI 自动判断的属性，用同一套属性定义 |
| 自动化 | 内置的几条 | 内部按“触发条件 → 条件 → 动作”执行，以后开放可视化编辑 |
| 权限 | 主管理员、管理员、组长、坐席 | 角色由权限组合而成，以后可以自定义角色 |
| 多工作区 | 一个账号可以属于多个工作区 | 开源后同一套部署服务多个团队；商业化时按工作区计费 |
| 界面语言 | 中文 | 文字都走翻译文件，以后加英文界面，服务开源社区 |
| 模型 | 翻译用的模型接口可以配置 | 每种用途分别配置模型接口，不绑定某一家供应商 |
| 接口 | 每个功能都有 API | 第三方和以后的桌面端、App 用同一套 API |

## 17. 路线

| 阶段 | 内容 |
|---|---|
| 1. MVP | 见第 15 节 |
| 2. 客服完善、AI 助手 | 工单、SLA、接待上限、按规则指派；知识库；AI 助手；邮件、Telegram 渠道 |
| 3. AI 客服 | AI 客服的训练、测试、上线、分析；帮助中心；WhatsApp；数据连接器 |
| 4. 内部沟通、Telegram 融合 | 成员之间的单聊、群聊；以成员身份连接 Telegram；桌面端 |
| 5. 内部服务、综合工作台 | 内部工单；把会话、工单、请求、待办汇总到一个工作台 |
| 6. 开源、商业化 | 英文界面、安装文档、云服务、许可证 |
