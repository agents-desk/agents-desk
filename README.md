# agents-desk

开源、AI 原生的团队沟通和服务平台。团队在这里接待客户、互相沟通、处理内部事务，AI 和成员一起完成这些工作。

## 1. 愿景

agents-desk 先服务我们自己的团队，同时从第一天起开源。

| 现状 | 要解决的问题 |
|---|---|
| 主要客户是印度人，客服是华人 | 客户用英语、印地语、Hinglish 提问，客服依赖外部翻译，回复慢、容易错 |
| 客户咨询需要有人跟进到办完 | 咨询散落在聊天记录里，容易被遗漏；每个咨询需要工单、负责人和时限 |
| 团队和合作方依赖 Telegram，内部沟通用个人微信 | 信息分散在几个工具里；团队需要一个能沉淀信息、连接业务系统的地方 |
| 大量重复的问题和手续 | 占用人力，可以交给 AI |

**覆盖的场景：** 客户服务（售前转化、售后支持）、团队沟通、内部服务（找 IT、人事、行政办事）。以后在这之上加入审批、考勤、wiki、任务等应用。

**原则：**

1. 聊天体验和微信一致，客户在自己习惯的渠道上联系我们。
2. 每个请求都形成工单，有人负责到底。
3. AI 按规则做事，放权的程度由数据决定；人随时可以接手，AI 可以一键停用。
4. 每一步都有记录。
5. 口子留在接口上，具体功能用具体代码实现，同类需求出现第三次再抽象。

## 2. 顶层设计

### 2.1 内核概念

| 概念 | 是什么 |
|---|---|
| 工作区 | 一个团队的空间，包含它的成员、数据和配置 |
| 参与者 | 能做事的一方：成员、团队、联系人（客户、合作方）、AI 智能体、系统 |
| 房间 | 一切会话的容器：客户会话、单聊、群聊、桥接会话。成员分内部方和外部方 |
| 事件 | 房间时间线上只追加的记录：消息、状态变化、卡片。带可见范围（所有人 / 仅内部）和派生内容（译文、语音转写） |
| 动作 | 一个有明确输入输出的操作，例如发消息、分配工单、查询订单 |
| 判定 | 决定一个动作是否执行的唯一入口 |
| 工作项 | 一件有负责人、阶段和期限的事：工单、商机、跟进任务、建议操作 |
| 连接器 | 外部聊天网络的适配器：网页插件、Telegram、WhatsApp、公众号、邮件、桥接 |
| 业务集成 | 外部业务系统（订单、物流、支付）的接入，把它们的能力变成动作 |

### 2.2 四个口子

以后最难改的四处现在定下来，其余部分按需实现：

1. **统一写入路径。** 所有操作都走“动作 → 判定 → 执行 → 提交后分发”。执行时在一个事务里写业务表和事件；提交后由任务队列分发给实时推送、翻译、AI、连接器、统计。
2. **统一判定入口。** 权限、接待模式、风险等级、额度、营销许可、一键停用都在这一处判断，人和 AI 遵守同一套规则。每次判定记录是哪条规则起的作用。
3. **连接器接口。** 每个渠道是一个连接器，以团队的身份（机器人、商业号、公众号）或成员本人的身份（桥接）收发消息。连接器可以独立部署，用任何语言编写。
4. **业务集成接口。** 外部系统通过 MCP 或 OpenAPI 接入，它们的能力成为动作，同样经过判定。

```
外部消息 ─► 连接器 ─┐
界面、API ─────────┤
AI 智能体 ─────────┼─► 动作 ─► 判定 ─► 执行（一个事务：业务表 + 事件） ─► 分发
自动化 ───────────┘                                           ├─ 实时推送
                                                              ├─ 翻译、转写
                                                              ├─ AI 响应
                                                              ├─ 连接器发出
                                                              └─ 统计
```

### 2.3 AI 智能体

AI 和成员一样是参与者：可以加入团队、负责工单、被 @、被单聊。

- **必须有负责人**；配置（模型、指令、知识）有版本，可以回滚。
- **三种执行身份：** 以自己的身份；代表某位成员（以这位成员本人的权限为上限）；自动执行（由定时、回调触发，只做只读和低风险操作）。
- **对客户标明是 AI。** 客户随时可以要求转人工，这条规则始终生效。

**动作的风险等级：**

| 等级 | 例子 | AI 能否执行 |
|---|---|---|
| 只读 | 查订单、查物流、查知识库 | 能 |
| 低风险 | 改工单字段、转人工、建跟进任务、发知识库链接 | 能 |
| 高风险 | 退款、改订单、发放物品、开通权限、批量发送 | 生成**建议操作**卡片，由成员确认后以自己的身份执行 |

**外部内容的防护：** 客户消息只作为数据，放在发给模型的用户消息里；客户身份由代码从会话中取；高风险操作由成员执行；AI 回复中声称完成的操作，要有对应的成功记录才发出。

**接待模式**（按团队和工单类型设置）：AI 接待（全自动）、AI 接待（人工审核）、人工接待（AI 辅助）、纯人工接待。新团队默认人工接待（AI 辅助），按质检数据逐类放权，指标变差自动退回。

### 2.4 模型调用

每种用途（翻译、向量、重排序、语音识别等）配置一个模型接口：地址、密钥和模型名，不同用途可以使用不同的接口和供应商。接口的协议不预设为 OpenAI 兼容，例如重排序使用各家的 rerank 接口，由这种用途的调用代码按它的接口实现。供应商的选择、故障切换和价格由这些接口负责。

- 每次调用带上业务标签：工作区、智能体、运行、用途。
- 费用以接口返回的数字为准，按用途和智能体汇总；预算用完时，AI 转人工并通知负责人。
- 向量、语音识别、翻译、判断、回复客户使用固定的模型名；个人助理、坐席辅助可以使用通用对话的模型名。
- 更换向量模型时重建索引。

### 2.5 工程约定

- 主程序打包为单个可执行文件；需要单独部署的连接器（例如 Telegram 桥接）作为独立进程运行。
- 每个架构决定记录在 `docs/adr` 中。

## 3. 第 1 阶段详细设计

**目标：** 印度客户的网页咨询全部在 agents-desk 中处理，坐席用中文工作，翻译在 agents-desk 中完成。

**范围：** 网页聊天插件、客户会话、工单、工作台、双向翻译、纯人工接待、联系人的阶段和来源、自行部署。第 1 阶段由坐席接待客户，模型只用于翻译。

**实现计划：** 见 [第 1 阶段的 PR 计划](docs/phase-1-prs.md)。

### 3.1 角色

| 角色 | 做什么 |
|---|---|
| 坐席 | 领取、回复、转接、解决工单 |
| 组长 | 分配工单，查看本组数据，设置本组的工作时间和 SLA |
| 管理员 | 管理成员、团队、网页插件、翻译设置 |
| 客户 | 在官网的聊天窗口里提问，直接在网页上使用 |

### 3.2 网页聊天插件

- 官网嵌入一段脚本，右下角出现聊天窗口。每个插件设置一个默认团队。
- **访客识别：** 访客用浏览器中保存的访客编号识别。客户在官网登录后，官网把签名过的客户身份传给插件，客户成为已验证的联系人，换设备也能看到历史。
- 客户关闭页面后再回来，看到完整的历史和坐席的回复。
- 消息显示发送状态：发送中、已送达、已读。

### 3.3 会话和工单

- 同一位客户在同一个插件上只有一个客户会话，像微信聊天窗口一样一直保留。
- 会话中的消息归入工单。第 1 阶段按规则归入：消息归入会话中进行中的工单；会话中的工单都已关闭时，新建工单；坐席可以合并、拆分工单，或把消息移到另一张工单。
- 已关闭的工单保持关闭。客户就同一件事再来时，新建工单并关联原工单。

**工单字段：** 编号、标题（坐席填写）、类型、请求人、渠道、团队、负责人（为空表示在队列中）、状态、优先级、SLA 期限、自定义字段、内部备注。

**状态：**

| 状态 | 含义 |
|---|---|
| 新建 | 刚创建，等待受理 |
| 处理中 | 等负责人推进 |
| 待回复 | 已回复或提问，等客户答复 |
| 挂起 | 等第三方结果 |
| 已解决 | 已办完，观察一段时间确认问题解决 |
| 已关闭 | 结束，只读 |

| 从 | 到 | 触发条件 |
|---|---|---|
| 新建 | 处理中 | 坐席领取，或组长指派 |
| 处理中 | 待回复 | 负责人回复 |
| 待回复 | 处理中 | 客户发来新消息 |
| 待回复 | 已关闭 | 等待期结束：提醒客户一次后再过 24 小时 |
| 处理中 | 挂起 | 负责人标记等待第三方 |
| 挂起 | 处理中 | 第三方结果返回，负责人恢复 |
| 处理中、待回复 | 已解决 | 负责人标记已解决 |
| 已解决 | 处理中 | 客户表示问题仍在 |
| 已解决 | 已关闭 | 48 小时的观察期结束 |

**分配：** 坐席从本组队列领取，组长指派，或者转接给其他坐席或团队。两人同时领取时先到者生效。SLA 到期时，工单退回队列并提醒组长。

**SLA：** 按团队和优先级设置首次响应和解决时长，按团队的工作时间计算；工作时间按团队设置时区，服务印度客户的团队按印度时间设置。

### 3.4 双向翻译

每位成员设置自己的工作语言。每条消息保存原文，读者看到译成自己语言的版本，可以切换查看原文。

| 步骤 | 发生了什么 |
|---|---|
| 1 | 客户发来 “mera order abhi tak nahi aaya”。系统识别为 Hinglish，坐席看到“我的订单到现在还没到” |
| 2 | 坐席用中文写回复 |
| 3 | 回复框下方显示即将发出的 Hinglish 译文，以及把译文再译回中文的结果，坐席确认后发送 |
| 4 | 客户收到 Hinglish 回复 |

- 每条消息单独识别语言和书写方式（例如用拉丁字母写的 Hinglish），客户换语言，回复跟着换。
- 术语表中的产品名、品牌名按固定译法翻译；订单号、金额、链接保持原样。
- 用中文或原文都能搜索到消息。
- 首批语言：英语、印地语、Hinglish。
- 翻译使用固定的模型名；翻译失败时消息照常显示，译文稍后补上。

### 3.5 工作台

坐席打开 agents-desk 看到：

| 视图 | 内容 |
|---|---|
| 我的工单 | 我负责、状态为处理中的工单，按 SLA 剩余时间排序 |
| 待领取 | 本组队列中的工单 |
| @我 | 内部备注中提到我的 |

工单详情：左边是会话（译文和原文），右边是工单字段、联系人资料（阶段、来源、历史工单）、内部备注、操作记录。

### 3.6 联系人

- **阶段：** 访客、线索（留下联系方式）、客户（已成交）、复购客户。第 1 阶段由坐席手动调整。
- **来源：** 第一次进来时的页面、来源网址和广告参数，自动记录。
- 这两项第 1 阶段就开始记录，第 3 阶段做转化统计时直接使用。

### 3.7 权限和可见范围

| 内容 | 客户 | 坐席 | 组长、管理员 |
|---|---|---|---|
| 客户会话 | 自己的 | 本组的 | 管辖范围内的 |
| 内部备注 | 隐藏 | 本组的 | 管辖范围内的 |
| 联系人资料 | 自己的 | 本组接触过的 | 管辖范围内的 |

所有操作记入操作日志：谁、什么时间、做了什么。

### 3.8 第 1 阶段要实现的内核

| 内核部分 | 第 1 阶段的最小实现 |
|---|---|
| 参与者 | 成员、团队、联系人；联系人的外部身份（网页访客编号、已验证的客户编号） |
| 房间和事件 | 客户会话；消息、状态变化、内部备注；译文作为派生内容 |
| 动作和判定 | 写入路径完整实现；判定只有角色权限一类规则 |
| 工作项 | 只有工单一种类型 |
| 连接器 | 网页插件，按连接器接口实现 |
| 模型调用 | 只用于翻译：一次调用同时识别语言和书写方式并给出译文 |

### 3.9 配置项

| 配置项 | 默认值 |
|---|---|
| 成员、团队、组长 | 按需设置 |
| 工作时间和时区 | 周一至周五 9:00–18:00，团队所在时区 |
| 网页插件和默认团队 | 按需设置 |
| 工单类型和自定义字段 | 按需设置 |
| SLA | 首次响应：工作时间内 30 分钟 |
| 自动关闭 | 待回复：提醒后 24 小时；已解决：48 小时 |
| 翻译：成员工作语言、术语表 | 中文 |
| 各用途的模型接口：地址、密钥和模型名 | 按需设置 |

### 3.10 指标

首次响应时长、平均解决时长、SLA 达成率、跟进工单率（关闭后客户就同一件事再次发起工单的比例）、翻译修改率（坐席看到回译后修改原文再发送的比例）、翻译费用。

## 5. 开发

### 5.1 开始

需要 Go（版本见 [go.mod](go.mod)）、[Bun](https://bun.sh) 和 Docker：

```bash
bun install
docker compose up -d --wait      # PostgreSQL 和 NATS
printf 'crypt:\n  key: %s\n' "$(openssl rand -base64 32)" > config/local.yaml   # 应用密钥，只在本机
go run ./cmd/agents-desk migrate up
go run ./cmd/agents-desk seed    # 开发用的账号和示例工作区，密码都是 password
bun run dev      # 工作区端在 http://localhost:8081，管理员端在 /admin/，接口文档在 /api/docs、/admin/api/docs
bun run build    # 构建 bin/agents-desk
```

用 `admin@example.com` / `password` 登录管理员端，可以看到示例工作区 `demo`；它的主管理员 `owner@example.com` / `password` 登录工作区端 <http://localhost:8081/>，进入 `/t/demo/`。生产环境不运行 `seed`，第一个平台管理员用 `admin create --email <邮箱>` 创建，密码在终端中输入。架构上的决定见 [docs/adr](docs/adr/README.md)。

目录、常用命令、提交前的检查和代码约定见 [AGENTS.md](AGENTS.md)，框架的文档在 `.tenon/docs` 中（`bun run dev` 时生成），也可以在线阅读 [Tenon 文档](https://github.com/go-tenon/tenon/tree/main/docs)。

### 5.2 AI 编程助手

#### Tenon 自动接入的

`tenon init` 和 `bun run agents`（`go tool tenon agents`）为 Claude Code、Codex、Cursor、Antigravity 准备好了这些，升级框架后运行 `bun run agents` 更新（`AGENTS.md` 由项目自己维护）：

- `.tenon/docs`：与 `go.mod` 中的框架版本一致的文档；
- `tenon-*` 技能：新增业务动作、写接口、加表、写页面等常做的事的步骤；
- MCP 服务 `tenon`（`go tool tenon mcp`）：检索框架的文档、查看项目信息、读 `bun run dev` 的输出。

选择接入哪些助手见 `.tenon/docs/installation/ai-assistants.md#choosing-assistants`。

#### 依赖的官方方案

项目用到的 Go、Mantine、TanStack 等也为 AI 编程助手提供了文档、MCP 服务和技能，按它们的官方方法接入。它们的写法与 Tenon 的约定冲突时，以 `AGENTS.md` 和 `.tenon/docs` 为准。

这个项目已经按下面的方法接上了 gopls、Mantine 的 MCP 服务和技能，以及 TanStack Router 的技能，配置都已提交；更新依赖的技能时重新执行对应的命令。

下面以 Claude Code 和 Codex 的命令为例。Claude Code 的命令加上 `-s project` 时写进项目的 `.mcp.json`，提交后团队共用。Cursor（`.cursor/mcp.json`）、Antigravity（`.agents/mcp_config.json`）在 `mcpServers` 中加上同样的 `command` 和 `args`，VS Code（`.vscode/mcp.json`）写在 `servers` 中。`bun run agents` 只改写其中的 `tenon` 一项，你加上的服务保持原样。

**Go：gopls**（[官方说明](https://go.dev/gopls/features/mcp)）。Go 的语言服务，在项目和依赖（与 `go.mod` 的版本一致）中查找符号、读包的 API、检查编译错误：

```bash
go install golang.org/x/tools/gopls@latest
claude mcp add gopls -- gopls mcp
codex mcp add gopls -- gopls mcp
gopls mcp -instructions    # 输出给模型看的使用说明，可以放进助手的上下文
```

Go 的其他依赖（Huma、chi、Bun ORM、goose 等）用 `go doc` 读与 `go.mod` 一致的版本，例如 `go doc github.com/danielgtaylor/huma/v2.Register`。

**Mantine**（[官方说明](https://mantine.dev/guides/llms/)）。文档目录 <https://mantine.dev/llms.txt>；MCP 服务查组件的属性和用法：

```bash
claude mcp add mantine -- npx -y @mantine/mcp-server
codex mcp add mantine -- npx -y @mantine/mcp-server
```

需要时安装 Mantine 的技能，例如表单、自定义选择框：

```bash
npx skills add https://github.com/mantinedev/skills --skill mantine-form
npx skills add https://github.com/mantinedev/skills --skill mantine-combobox
```

**TanStack Router、Start、Query**。文档目录：<https://tanstack.com/router/latest/llms.txt>、<https://tanstack.com/start/latest/llms.txt>、<https://tanstack.com/query/latest/llms.txt>。Router 和 Start 的包中带有技能，版本与安装的包一致，用 [TanStack Intent](https://tanstack.com/intent/latest) 接入（在终端中交互选择）：

```bash
bunx @tanstack/intent@latest install
```

选择时只启用 `@tanstack/react-router`、`@tanstack/router-core` 的技能：这个项目的业务逻辑都在 Go 的接口中，前端只负责展示和交互。

**React、Vite、Bun**。文档目录：<https://react.dev/llms.txt>、<https://vite.dev/llms.txt>、<https://bun.com/llms.txt>。
